## D155 · Deterministic first: code decides everything it can, an AI only words or picks among what code laid out, and this rule wins over earlier decisions — 2026-11-07
Strengthens D18 and holds every built and planned step:
- **Code decides** whatever the code, graph or document can settle: structure, scope, bundle contents, candidates, what's missing, every id and quote.
- **An AI may only** (a) word a structure code chose, (b) pick among options code listed, or (c) make the one judgement code can't, cut as small as code can. Never "find everything" or "decide what matters".
- **Code checks every AI output;** where it can't check meaning, a person approves. A step code can do with a fixed rule or template is done by code.

- **A change to anything built or planned is said plainly, and waits for the owner's OK.** Nothing changes silently.

**Why:** hallucination can't be checked away afterwards; the less an AI decides, the less it can make up. **Cost:** more code, and blunter steps (a template reads stiffer).

## D178 · Areas by a fixed folder rule; ties are listed for a person, never broken by code — 2026-11-09 (owner: "Yes, folder rule", on the recommendation)
Settles D176 item 6, replacing D154's route-first-segment rule (D170).
1. **Home folder:** each flow's home is the folder its screen's code sits in (Sonarr `frontend/src/<X>`, Kavita `src/app/<x>`, nopCommerce `Views/<Controller>`; an MVC area's views one level down under that area's group, `Areas/Admin/Views/Product` → Admin › Product). A click flow takes its screen's home.
2. **Shared folders are never a home:** a folder whose screens are used by more than one route's screens (Sonarr `Components`, Kavita `shared`, nopCommerce `Views/Shared`); a flow there takes the home of the screen that shows it, several → a tie.
3. **Jobs and handlers:** the area whose flows link to them most; none → the backend folder of their class (`NzbDrone.Core.Tv` → Tv), D154's backend-only areas; an even count → a tie.
4. **Size:** over 40 flows splits by the next folder level (Sonarr Settings → Settings/Indexers); code never merges.
Ties are listed in `areas.yaml` for the person; after the person's edit, code checks every flow is in exactly one area. With no folder structure, code says "areas need a person" instead of guessing.

**Why:** folders are the one grouping all three stacks share (routes fail on Kavita and nopCommerce, D170). **Cost:** stiff folder names to rename once; Kavita's readers come out as three areas; nopCommerce gives 18 public and 57 admin areas to confirm.

## D179 · What every flow shows: name, start, actor, inputs, checks, steps, ends, scenarios, links, guesses, settings — all by code — 2026-11-09 (owner: "okay sure", on the recommendation; asked first: "do we show the actor and what not also, the scenario or flow, validation rules and etc")
- **Parts:** name (D176), start (D171), actor, inputs (a form's fields or the request body's shape), checks (`rule` facts per input with message, "only warns" from modifiers, D174), steps with quoted conditions (D172, D174), ends (D172, D174), scenarios, links (D173), guesses and ❓ (D175), settings (D176).
- **Actor, a fixed rule:** the screen's route guard plus the access rule on the first endpoint the flow calls: `[AllowAnonymous]` → anyone; a fallback "must be signed in" → signed-in user; a permission filter → "user with permission Customers.Manage"; a job → system, with its schedule when constant. A later step that needs more says so on that step ("needs `Orders.Manage`"). Only `denies` and `name` evidence counts (D167); otherwise the actor is 🟡 with its reason.
- **Scenarios, bounded:** the main path (no early exit taken) plus one scenario per early exit with the conditions on the way to it ("Registration disabled: `UserRegistrationType == Disabled` → register result page"). Never every combination of conditions (nopCommerce's Register has about 25). They pair with an FSD's numbered alternate flows (D160).
- **Messages a user sees:** a rule's `WithMessage` and an exit's error text when constant, through the app's translation file; else the key.
- **Not shown:** screen layout and field order (screen behaviour, not a flow).

**Why:** an FSD states who, what they enter, what's checked, what happens and the alternatives; a flow without them can't be compared step by step. **Cost:** long flows; the actor rule reads only the first endpoint's access, so a flow whose later steps differ carries per-step notes.
