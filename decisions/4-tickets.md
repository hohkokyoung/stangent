# Decisions D69–D98: tickets

## D69 · Phase 3's bundle is read by a developer's Claude Code first; Phase 4 reads the same contract — 2026-10-25
A developer runs `/stangent:ticket PROJ-123`. The CLI builds the bundle by code: JSON for the agent and a short Markdown view for the developer. Phase 4's planner later reads the same `ticket-bundle` contract unchanged. **Why:** useful from day one, and a person using it shows what a bundle needs before agents depend on it. **Cost:** a developer's session isn't a measurement; the proof needs its own scored benchmark.

## D70 · A ticket's starting points: code's signals, and the developer's edits — 2026-10-25
Code finds exact signals in the ticket: a stack-trace frame → its method; a URL path → the route's page; a quoted screen name, page title or FSD section title → those pages; a symbol name in the graph. The developer can add or remove points before work starts, and the bundle records who changed what. **Why:** code takes the certain cases at no cost. **Cost:** a ticket that names nothing code can match gets no point from code. Parts replaced by D101: the AI picking pages from page titles; code's signals are now the fallback when the finder is off. D156 P6 may make them first again, once Phase 3's numbers are checked on code alone.

## D71 · The bundle carries pages and pointers, not source code, under a size cap — 2026-10-25
Built by code: the ticket and attachments, the starting points with reasons, the reference pages and their linked FSD sections (link state, whether a person decided), the impact answer within 2 lines, and pointers to files and symbols. No source code. Cap ~40k characters, a setting. Missing or stale pages are flagged, never generated by the bundle. **Why:** pages are Phase 2's checked summary of the code, the cheapest grounded context. **Cost:** on a repo with few pages the bundle is mostly pointers. What gives way under the cap is replaced by D101 (starting points never cut, impact lists first, then pages).

## D72 · Attachments: code converts text, keeps images as files, lists the rest — 2026-10-25
Code downloads every attachment, with its content hash. Text files go in up to a per-file cap, and their stack traces feed the starting points. `.docx` and `.pdf` go through the import steps (D121); one that can't be read is listed with why. Images are saved and listed; no stangent AI step describes them. Excel, video and the rest are listed by name, type and size. **Why:** what's deterministic is converted by code; the rest stays as it is. **Cost:** an agent without vision gets nothing from a screenshot but its name.

## D73 · The stangent CLI reaches Jira as an MCP client, behind the issue-tracker adapter — 2026-10-25
The C# CLI calls Atlassian's MCP server from code (no AI in the fetch path), with its own browser sign-in and the refresh token in the OS keychain. Unattended runs use the API-token sign-in, which an admin must enable. A file backend reads tickets from JSON for tests and the benchmark. Code reads only fields it names and keeps the raw result's hash. **Why:** one integration Atlassian maintains, with OAuth locally. **Cost:** MCP tools aren't versioned like REST, so output can change under stangent; unattended use needs an admin. Endpoint and scopes: D82.

## D74 · Write-back: drafts as files; a person reads and posts them — 2026-10-25
Two drafts, never posted by stangent: questions at pull time (unclear ticket, or a clash with the FSD or a page, quoting both sides word for word) and a resolution summary from the merged PR. Tone `internal` or `client`. Code checks every claim links to a real page, section, file, PR or ticket sentence; a client draft has no code names or paths. The developer posts it with `stangent ticket post` under their own login. Phase 3 writes nothing else to Jira (no transitions, no field edits). **Why:** a wrong comment can't be unsent. **Cost:** every comment waits for the developer. The AI writing the words is replaced by D156 P7 (code templates, AI only rewords).

## D75 · A bug is proven before it's fixed, in Phase 3 — 2026-10-25
A bug ticket (by issue type, a setting) gets a reproduction test from an AI step. Code checks it compiles and fails on an assertion that checks the ticket's expected result. Reproduced: the fix must make it pass and break nothing else. Not reproduced: Phase 3 says "no proof yet" and why (D106); from Phase 4 an agent waits for a person's go. A developer can add a hint (`ticket prove --hint`) for a new, checked attempt. The proof is advice only (D109). **Why:** a fix for a bug that isn't there wastes time and can break correct code. **Cost:** an AI test can be wrong either way, so a person confirms.

## D76 · Bug proof uses unit tests and Playwright — 2026-10-25
The reproduction goes into the repo's own unit-test project (no databases or services). UI bugs use Playwright against the running app; how to build, start and seed it is a per-repo setting (`tickets.app`), never invented. Without it, a UI bug is "not provable here". A Playwright reproduction counts only if it fails the same way 3 runs in a row. Integration tests stay in Phase 5. **Why:** many bugs are about what a screen shows. **Cost:** the start-and-seed setting is real work per repo; browser runs are slower and flakier.

## D77 · Phase 3 is proven on Sonarr issues copied into the owner's Jira, read through the MCP — 2026-10-25
Real Sonarr issues, each closed by a main-line fix commit, copied once into a Jira project and read through the MCP as in real use. The first read saves each raw result; scoring replays them, so a re-score is repeatable. The answer key is git history (the fix's files; the test fails on the parent and passes on the fix), never put in a bundle. **Why:** real tickets with known fixes give a score by code. **Cost:** older issues are scored against today's graph and pages.

## D78 · The frozen set: 40 bugs and 10 not-bugs — 2026-10-25
40 Sonarr bugs, newest first before the pinned commit, each fixed by one main-line commit of at most 15 files, labelled backend, frontend or both; plus 10 not-bugs (closed as not a bug, by design or can't reproduce). Chosen by a code rule, frozen and committed. Bundles run on all 50; reproduction on the 30 newest bugs and the 10 not-bugs (D81). Sonarr's 40 are now the tuning set (D100). **Why:** enough bugs for the bars; not-bugs test why bugs are proven first. **Cost:** change requests aren't scored; 40 cases give wide ranges.

## D79 · Phase 3's done-when: right place, real proof, grounded, repeatable — 2026-10-25
Bars, agreed before any run, with 95% ranges: right place ≥ 70% of 40 bugs and beating a keyword search; grounded and repeatable (byte-identical replay, zero AI calls on a re-run) and the Jira round trip are must-pass, a failure is a bug to fix; proof is real ≥ 90% pass on the fix; proof finds bugs ≥ 50% of 30; at most 1 of 10 not-bugs reproduced. If a proof bar fails, the proof ships as advice only. Bars never move after a run. **Why:** a pre-agreed bar can't drift. **Cost:** one case moves a share by 2.5 points. The fallback "AI picks off by default" is obsolete: D101's finder replaced the picks.

## D80 · "code-wrong" decisions don't become tickets in Phase 3 — 2026-10-25
Changes D58. Phase 2 already lists them in `specs/trace.yaml`; a person who decides "code-wrong" makes the ticket by hand. **Why:** these are differences between the FSD and the pages, not confirmed bugs. **Cost:** the step from a decision to a ticket stays manual.

## D81 · The run's cost: reproduction on 30 bugs, each attempt capped — 2026-10-25
Bundles and drafts run on all 50 tickets; reproduction on the 30 newest bugs and the 10 not-bugs. Each attempt is capped at $1 and 30 turns (D86), the same per-ticket limit real use has (`tickets.proveBudget`); an attempt that hits it is "not reproduced". **Why:** cut where the money is, keep the bundle bars on 40 cases. **Cost:** the proof's ranges are wide (about ±18 points); 10 not-bugs catch only gross failure.

## D82 · Jira through Atlassian's MCP v2 (`/v2/mcp`), with Jira-only scopes and secrets in the OS keychain — 2026-10-25
Endpoint `https://mcp.atlassian.com/v2/mcp` (v1 has no attachment download). stangent calls operations by fixed name through `executeRead` / `executeWrite`, never `discover` at run time. OAuth asks only for the three Jira agent-interface scopes plus `read:me`, `read:account`, `email`, `offline_access`. Secrets live in the OS keychain through the OS's own API, never on a command line, in a file or in an error message (a `security -i` write once echoed a token). **Why:** v2 has what Phase 3 needs; fewer scopes limit a leak. **Cost:** a renamed operation fails at run time; the adapter tests on saved results catch it.

## D83 · A ticket's parts can be marked "outside the code" (server, network, deployment, data), each tagged by who said so — 2026-10-26
Beside its code starting points, a ticket can have outside-the-code parts, each with an area and the ticket's words as evidence, tagged `ai` (quote checked word for word) or `developer`. Code doesn't guess them. The bundle shows both. Proof is skipped (`not-provable`, `outside`, no AI call) only when every part is outside and nothing points into the code. UI, API and app-level security bugs are always in the code. **Why:** a code bundle for an infra problem misleads and wastes a proof. **Cost:** a mixed ticket still pays for an attempt.

## D84 · Drafts: framing lines need no claim, writers never talk about their input, and the run drafts after proof — 2026-10-26
Exempt from the claim rule: questions, a short greeting, a heading, or a lead-in phrase of eight words or fewer ending with a colon. A bold label followed by a sentence is a claim. Writers never mention "the input" or their instructions, link `missing` only to a listed missing field, and say nothing about how a fix was checked without a proof. Drafts run after proof. **Why:** the checker should stop made-up claims, not greetings. **Cost:** a short heading or lead-in can still state a small claim unmarked (shown as "not checked", D98).

## D85 · A Jira read that gets no answer is tried again, the last time on a new session — 2026-10-26
Reads (a fixed list) get 30 s a try and 3 tries; the third opens a new MCP session. Writes get one try of 7 minutes, since a retry could post twice. The limits wait while the browser sign-in page is open. **Why:** a pull hung for an hour and stopped a batch. **Cost:** a read slower than 30 s fails after three tries; the new-session path isn't tested live.

## D86 · Browser proof: the app runs while the AI works; it copies a related Playwright test, or looks with a browser — 2026-10-26
stangent starts the app (`tickets.app`) before the attempt and stops it after; its own check starts it fresh and runs 3 times. Code finds the repo's specs whose `goto` path matches a bundle screen and runs them first; the AI copies the closest. With none, it gets a headless browser limited to the local app. The AI runs its test and hands it in only once it fails on the named assertion. The test is kept for the developer. Guards: the app never outlives the command, no user or project Claude settings, writes limited to the result. Cap: 30 turns, $1. **Why:** a test that never saw the page fails on the wrong thing. **Cost:** every click is a turn; not a sandbox.

## D87 · Starting points through a page index built by code; ranking orders pages, it never hides one — 2026-10-27
Code builds a page index (titles, routes, code names, statements, FSD sections, the code's own text) and ranks pages against the ticket's words. Ranking only orders; it never hides a page, and there's no code-picked "clear winner". When there's no confident point, the bundle says so and the questions draft asks where. **Why:** missing the right place is the worst outcome. **Cost:** words that differ between ticket and code rank low. **Uncertain:** D101 took the index out of starting points (kept for benchmark measures); D156 P6 may change this after Phase 3's numbers are checked.

## D88 · Impact answers say what they left out; no forward walk — 2026-10-28
A depth limit reports, per group, how many items and ❓ it left out. Files the graph can't read (Razor views, project files, `using` edits, stylesheets, migrations, `package.json`, lock files) are listed as ❓, until the graph learns them. No forward walk (what changed code uses): the compiler and tests cover it. Impact answers keep their order; no ranking by meaning. Built with D65 as `impact-report` v6. **Why:** D27 promises every ❓ is listed. **Cost:** longer answers; the unread-file list must track what the graph learns.

## D89 · Our own setup never counts against the AI — 2026-10-31
1. Permission rules and the result file use absolute paths, and each command starts back in the repo (`CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1`). 2. A refusal of what stangent's own rules allow makes the attempt `failed` with `setupBlocked: true`: no retry, the batch stops, the next run tries again; the score lists these apart. 3. A start command that exits non-zero fails at once with its error. 4. Unit targets come from the code at every starting point (a page point is its entry). **Why:** a score mixing our bugs with the AI's misses tells no one what to fix. **Cost:** a failed attempt's spend is lost; a symlinked path isn't recognised.

## D90 · A test runner that can't run is the setup's failure; a mock's own check is an assertion — 2026-11-01
With no test result, stangent lists the project's tests: none listed means `runner-error`, a setup failure (D89); tests listed means the test crashed or was misnamed, and the reproducer retries. Moq, NSubstitute and FakeItEasy expectation failures, and NUnit's trimmed format, count as assertions; a strict mock refusing a call is the code failing. **Why:** a score must not count the machine against the AI; mocks are how most C# tests check side effects. **Cost:** an extra `--list-tests` run when a name isn't found.

## D91 · A setup failure gets a plain reason and advice; stangent never installs anything itself — 2026-11-01
A setup failure stays `failed` and carries advice chosen by code from the error (missing runtime and how to install it, the app's start error, Node or Playwright, a runner with no tests, or "a stangent bug"); anything unknown gets the raw error. stangent never installs software or changes the machine; `/stangent:ticket` shows the advice. A batch still stops at the first setup failure. **Why:** a developer needs what to do, not a host error. **Cost:** a list of known errors to keep current.

## D92 · Must-pass fixes after the Sonarr run: drafts that stay sourced, a keychain that survives parallel runs — 2026-11-01
The claim check stays strict: a "Label: finding" line is a claim, and a request ("Please send…", "Could you…") counts like a question. Only one process at a time opens a Jira session with the shared sign-in (a lock file); the token cache rereads the keychain; a token that won't save is a warning; keychain calls retry a passing failure. A failed pull fails `ticket-run.sh`. **Why:** grounded and repeatable are must-pass (D79). **Cost:** longer writer instructions; a busy keychain can add ~1.5 s. Archived: the one-off benchmark fixes and re-run order (obsolete: done).

## D93 · A version given in the environment counts as the version — 2026-11-01
With no version field or heading, a "Label: value" environment line whose value holds a version number counts as the version. Lines naming the machine around the product (OS, browser, database, runtime, container, proxy, server) don't count; labels are judged word by word, and an IP address isn't a version. No product name is assumed. **Why:** asking for what the reporter already wrote makes the draft wrong. **Cost:** a plug-in's version may be read as the product's; the "around the product" list is a heuristic.

## D94 · The generality batch: nothing in stangent assumes the benchmark repos — 2026-11-01
Fixes that hold for any C# or TypeScript repo: MTP and VSTest test commands; a generated `.stangent.playwright.config.ts` beside the repo's own (its own `stangent` project, git-excluded); the proof's build gets the graph build's properties; test projects found through any chain of references; rank weights settable (`tickets.rank`); neutral instruction examples; general event-bus built-ins only; frontend wrapper verbs read from whole words. Open: Karma/Jasmine and Mocha targets. **Why:** each misbehaved on a plausible repo shape. **Cost:** stangent writes an untracked config file into the repo.

## D95 · A proof says which ticket sentence its failure shows; a developer confirms the match — 2026-11-01
The reproducer returns `actualQuote` (the ticket's actual-result sentence, word for word) and `shows` (words of the failure message that show it). Code checks the quote is in the ticket and `shows` is in every run's failure message and not in the test's own source; one retry. The developer sees both side by side and confirms with `ticket prove --confirm`; until then the proof is advice. Matching by code alone was tried and dropped: it was wrong both ways. **Why:** a checked side-by-side makes the call quick and honest. **Cost:** a person decides.

## D96 · A failing test shows the code differs from what the reporter expects; a person makes it a bug — 2026-11-01
`reproduced` reads as "the code does Y, the reporter expected X", a difference to decide, not a proven bug. Only a developer's `--confirm` (the reported problem, and a bug) makes it one. No AI judges bug versus intended (D18). A questions draft isn't to call an unconfirmed proof a bug. **Why:** code can't tell intended from broken; only what people wrote or decide can. **Cost:** a person makes every bug-or-not call. Archived: "bug, per R-0042" from approved requirements, replaced by D156 P4/P5 (code-cut sentences; the ticket matcher is parked).

## D97 · A draft leaves out a sentence no claim backs, instead of failing — 2026-11-01
Code leaves an unbacked sentence out of the draft and records it (`ticket-update` v1 `dropped`, shown as "Left out"); everything left is still checked. A greeting or thanks of 8 words or fewer needs no claim. A draft with nothing left gets the retry. Link and quote errors still fail the draft. **Why:** nothing unsourced reaches Jira either way; a draft lost to one stray line helps no one. **Cost:** the text can read abruptly; the person posting sees what was dropped.

## D98 · A draft is a list of parts, each one sentence with its claims — 2026-11-01
`draft-output` v2 is a list of parts, each one sentence or framing line with its claim ids. A part with a line break or a second sentence is an error (one retry). A part without a claim is kept only if it states nothing: a pure ask (no reason, no `:`, no "confirm"), or a greeting that is nothing else. One claim backs one part. Kept claimless parts are listed as "not checked". Code joins the parts into Markdown. **Why:** checking a list is exact; guessing sentences in prose isn't. **Cost:** "etc." costs a retry; a question with a reason needs a claim. The writer composing the parts is replaced by D156 P7 (code templates, AI only rewords).
