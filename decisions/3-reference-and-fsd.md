# Decisions D50–D68: reference pages and the FSD

## D50 · stangent is a standalone rebuild, modelled on the company's pipelines — 2026-10-19
stangent depends on nothing the company runs. Its pipelines (a cited spec from code; plan → reviewed change) are a shape to copy, not a system to plug into. Where stangent differs, the decision says why. **Why:** a proven shape beats inventing one. **Cost:** only a one-line description of the model is known, so the details are decided here.

## D51 · The spec is built from the agreed FSD and the code together — 2026-10-19
The agreed FSD and the code are always read together. Each item is labelled: both agree, documented only, code only, or conflict. Code adds what the FSD never mentions. With no FSD, the spec comes from code alone. On a conflict stangent picks no winner: BA/PM do (D15). **Why:** what the client signed off on is what the system owes; code shows what was built, not what was asked. **Cost:** document import stays in scope, and "does the code do what the FSD says" is the step code can't fully check (D18).

## D52 · Two documents, linked: the FSD and a reference generated from code — 2026-10-19
Three layers. **FSD:** converted to text by code, never rewritten by AI, sections keep their ids. **Reference:** pages on what the code does; every statement cites symbol ids that code checks; committed with its input hashes and commit. **Links + decisions:** section ↔ page, states agree / gap / undocumented / conflict; editing either end drops a link to unverified (D11). No AI rewrites the FSD into requirements (D156 P4). **Why:** less AI, a check per layer. **Cost:** two documents; links are many-to-many. Parts replaced: the outside document as the agreed one, by D128 (the parsed spec in the repo is the truth); D99's structured-spec layer, by D156 P4.

## D53 · Links: code finds candidates, AI judges, code checks, a person approves — 2026-10-19
1. Code finds the candidate pages for a section (by area once D154's trial wins). 2. The AI judges the link. 3. Code checks every id and quote exists word for word; a failed check never reaches a person. 4. A person approves: "agree" in bulk per chapter, findings one by one. Unapproved links are unverified. A quote is a sentence (≥ 4 words, or a whole cell, item or statement). A section whose pages have no recorded version fails, never becomes a gap. "Undocumented" covers only `fsd.scope`. **Why:** code does what it can; people look at findings. **Cost:** bulk approval can let a wrong "agree" through. Parts to be replaced (D156, built in its order): the AI quoting both sides, by P3 (the judge names ids, code fills quotes); the AI candidate finder fallback, by P2.

## D54 · Reference pages: ids from the graph, every statement cited — 2026-10-19
A page's id comes from the graph, never from an AI, so it's stable and found by code. Every statement cites symbols (D52). A page's input is the graph slice code cut for it. **Why:** stable ids found by code. **Cost:** a renamed route changes an id, so links need D10's rename repair. Parts to be replaced: one page per screen, backend pages, the 3-screens shared-component page and the slice rule, by D154 if its trial wins (nothing replaced yet; old and new live side by side, D156); the writer choosing what to say, by D156 P1.

## D55 · The reference catches up per change: detected on each PR, regenerated on merge — 2026-10-19
1. Every PR, code only: the graph diff lists the pages whose input changed, with their linked sections. 2. On merge to main: only those pages are regenerated, each recorded with commit and input hashes; links whose page text changed drop to unverified. 3. Per release, optional: a sweep for any missed. A per-repo no-AI switch turns step 2 off. **Why:** drift shows in the PR that causes it; AI runs once per merged change. **Cost:** AI calls in CI on merges; an unchanged page's inputs reuse the old page (D18).

## D56 · Links are scored on a Sonarr FSD with planted discrepancies — 2026-10-19
An FSD for Sonarr in our own words, with planted gaps, conflicts and undocumented items in an answer-key file. FSDs follow no standard, so it mixes numbered chapters and plain prose. Scored by code: planted items found, and unplanted findings, a sample hand-checked (D67). A real FSD run is still owed. **Why:** an answer key turns a count into a score. **Cost:** a planted FSD is tidier than a real one, so it overstates quality. Parts gone: the cyberbullying note, reversed by D127.

## D57 · The links' done-when: finds what's planted, not too noisy, grounded, repeatable — 2026-10-19
On 30 planted items (10 per kind). **Finds:** ≥ 80% overall and ≥ 60% per kind. **Not too noisy:** ≤ 30% false alarms. **Grounded:** everything in the queue passes the D18 checks. **Repeatable:** same file → same text; unchanged inputs reuse the AI output. A 95% range is reported beside each share. If finds or noise fails, findings ship off (D68). **Why:** a bar agreed first can't move to fit the numbers. **Cost:** one miss moves a kind by 10 points.

## D58 · Decisions are fields in a committed YAML file; the website later edits the same file — 2026-10-20
Each link and finding is an entry in a committed YAML file: section, page, state, both quotes, `decision` (agree / code-wrong / fsd-wrong / defer) and `decided_by`. A person edits `decision` in a PR; the Phase 8 dashboard edits the same file. CI checks the schema, drops a decision to undecided when a quote's hash no longer matches, and fills `decided_by` from git, never typed. An entry's id is a hash of its link and quotes. "code-wrong" stays listed; a person makes the ticket (D80). **Why:** a checked, attributed record the website reuses. **Cost:** YAML in a PR is clunky for BAs. Parts replaced: D99's requirement tick boxes, by D156 P4.

## D60 · AI steps run in Claude Code; the CLI prepares their input and checks their output — 2026-10-20
1. `prepare` (code) writes one bundle: input, instructions, output schema. 2. Claude Code writes JSON in that schema, with no access outside its working folder (enforced by permission rules). 3. `check` (code) validates schema, citations and quotes, and records the output with input hashes and model. A failed check gives one error for one retry. `prepare` and `check` name the next step, so drivers hold no logic. Locally on the user's Claude Code; in CI, headless `claude -p`. **Why:** the CLI stays deterministic; every AI output passes code. **Cost:** CI needs a token; tool limits are a setting, so `check` still rejects citations outside the slice. Parts replaced: the writer choosing what to say, by D156 P1.

## D61 · Verification by a separate agent with a fresh context — 2026-10-20
When an AI step judges whether work is right, a separate agent with a fresh context does it, given the work, the criteria and the evidence, not the author's reasoning. Code checks come first (D18). Findings are fixed or rejected with a stated reason. Capped: one fresh check and one fix round per build, narrow brief, cost stated first. Paused while building (D120). **Why:** an agent reviewing itself shares its blind spots. **Cost:** more tokens; more edge cases left as listed gaps.

## D62 · Phase 2 applies D61: a fresh verifier for pages and for "agree" links — 2026-10-20
**Pages:** a fresh verifier sees the bundle and page only and flags unsupported or contradicted statements; a "contradicted" one quotes a source line (≥ 12 chars, two tokens) that code finds. Findings go back for the writer's one retry; a fixed page isn't verified again. **Agree links:** a second fresh check before bulk approval; a disagreement becomes a finding. **Under review (D156 P8):** the agree checker stays only if the flows trial shows it helps. Report claims are checked by a fresh agent. **Why:** no step grades itself. **Cost:** about double the AI calls per page. Parts reversed: "no second check on every finding", by D119.

## D63 · Hubs are included, not walked into; slice limits are settings — 2026-10-20
A point with `spec.hubCallers` (10) or more callers is included but not walked into (logging, `translate()`, base services). Depths and the bundle cap are settings in `stangent.yaml` (`spec:`). **Why:** bounded slices, no hub dragging in half the code. **Cost:** a hub's own rules reach a page only through its own entry. Parts to be replaced: screens stopping at endpoints and a page for every endpoint, by D154 if its trial wins (nothing replaced yet; old and new live side by side, D156).

## D64 · The split check is judged on bitwarden's first run; no rerun — 2026-10-20
The verdict stands on that run (safe failed, D49). The cutter's fix is kept in the 1d harness for whoever tests a split rule next (D65). **Why:** a rerun after tuning would grade our own fix. **Cost:** one run's noise stays in the verdict.

## D65 · The graph's blind spots and a smarter split rule are Phase 4 work — 2026-10-20
The graph doesn't see Razor views, `.csproj` / `Directory.Build.props` and package versions, or `using` edits that change a name's meaning; hub types may over-join edits. Both go to Phase 4: the graph learns those files, and the splitter joins only through changed or affected points, each proven with the 1d harness. Merged build and test stay. **Why:** Phase 4 shapes the graph work it needs; all plain code. **Cost:** Phases 5–6 wait for it. **Uncertain:** D156's Phase 1 rebuild covers nopCommerce (server-rendered MVC), which may need Razor views before Phase 4. Owner decides. **Changed 2026-11-08 by D159:** the blind spots flows need are fixed in D156's graph check, not Phase 4.

## D66 · Sonnet writes and verifies pages, in single-turn calls; pages are made as needed — 2026-10-20
Each AI step is one call: input in the prompt, no tools, `--json-schema`, no settings, skills or MCP servers. Sonnet writes and verifies pages; a fresh hand-read found 2 wrong statements in 88, so Sonnet stays. The verifier isn't weakened to save tokens. Pages are made for what needs them, not all at once. **Why:** a bare call cut cost from $0.31 to $0.18 a page. **Cost:** the bundle is cached twice (writer and verifier schemas differ). Parts gone: the 2a proof set (~103 pages + 10 handlers) and the 718-page cost figures, obsolete once 2a was proven.

## D67 · Phase 2's hand checks are done by a fresh agent, not the owner — 2026-10-24
The noise check on unplanted findings and the page hand-reads are done by a separate fresh agent (D61), given the criteria, FSD, pages and source at the pinned commit, nothing about how they were made. One verdict per item, with reason and evidence. The author never marks its own work. Reports say an AI checked. **Why:** the noise bar stays measured by someone other than the author. **Cost:** the checker can share the judge's blind spots; a person's check is owed before relying on findings in a real project.

## D68 · Discrepancy findings ship off by default (D57's rule, applied) — 2026-10-25
Finds passed (27 of 30) but noise failed (31.3% vs 30%), so `fsd.findings` defaults to `false`: sections record only links; gaps, conflicts and undocumented items aren't written to `specs/trace.yaml`. A project opts in with `findings: true`; the Sonarr benchmark does. Turning it off or on re-runs sections. The bar isn't moved. **Why:** D57, agreed before any run. **Cost:** a project wanting the drift list accepts about one false alarm in three.
