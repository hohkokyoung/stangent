# The spec (Phase 2: contracts `reference-page`, `reference-lines`, `source-document` v3, `trace-links`)

"The spec" is three layers (D52), each with its own check:

| Layer | Where | Written by | Checked by |
|---|---|---|---|
| **Reference pages**: what the code does, per screen, shared component and backend entry point | `specs/reference/` | AI (Claude Code subagents, D60) | code: schema, every citation in the graph and in the page's slice; a fresh verifier (D62) |
| **The FSD**: the documents the client agreed, converted to text | `specs/fsd/<doc>/` | the client / BA; converted by code | same file → same bytes |
| **Links, findings, decisions** | `specs/trace.yaml` | AI proposes, people decide | code: quotes word for word, ids, cited symbols, `decided_by` from git |

Everything above is committed: AI output is stored, not regenerated (D18). The graph (D25) and the AI steps' working
files (`.stangent/spec/`, `.stangent/fsd/`) are not.

## How an AI step runs (D60, D61)

Every AI step is the same small loop. The CLI holds all the logic; a driver only runs the subagent each step names.

1. `stangent … prepare` writes the step's input as one file (instructions, output schema, the evidence) and prints
   `result.next`: `{action, agent, prompt, output}`, or `action: none` when nothing needs AI (inputs unchanged, D18).
2. The driver starts the named subagent from the plugin with exactly that prompt. Its tools are `Read` and `Write`.
3. `stangent … check [--usage <claude json>]` checks the output by code and prints the next step. A failed check
   gives the subagent **one retry** with the specific errors; a second failure is recorded as failed.

Drivers: `/stangent:spec-generate` and `/stangent:fsd-link` in a Claude Code session, and
`plugin/scripts/spec-run.sh` for batches and CI (headless `claude -p --output-format json`, so tokens, cost, model and
time are recorded per step; `--jobs N` runs pages side by side). The batch driver makes **one turn per call** (D66):
the step's input files go into the prompt, Claude Code runs with no tools and none of the user's settings, skills or
MCP servers (`--tools "" --setting-sources "" --disable-slash-commands --strict-mcp-config`), the output schema is
enforced with `--json-schema` (`next.schema`; `stangent spec schema <name>` prints it), and the driver writes the
structured answer to `next.output`, so `check` is unchanged and input hashes are the same in both modes. `--agents`
runs the plugin's subagents instead, each allowed to read and write only under `.stangent/`
(`--permission-mode dontAsk --allowedTools "Read(.stangent/**)" "Edit(.stangent/**)"`). Files
drivers share are written whole (temp file, then rename) under a lock. A section whose candidate pages have no recorded
version is reported as failed, never turned into a gap. `ai.enabled: false` stops every `prepare` with exit
code 4 (D24); `spec stale`, `spec cite`, `fsd import`, `fsd diff`, `fsd resolve`, `fsd promote`, `fsd discard`, `fsd candidates`, `fsd undocumented` and `trace check` are code only.

## What a bundle stores (D130)

A page writer's, page verifier's, link judge's or agree checker's file under `.stangent/` holds a pointer on its first line and what's unique to it. The one copy of the instructions and schema is in the program. `stangent spec assemble <file>` puts them back, byte for byte; the driver does this just before each call, and `--in-place` does it for a subagent that reads the file itself. Input hashes are taken on the full text, so saved pages and links stay valid, with `SavedWorkTests` and `SharedHeadTests` pinning it. Only the first line is ever read as a pointer. `spec bundle <page>` prints the full text, for people.

`schema-once` (off): batch runs send the schema through Claude Code's schema option only, not also in the text (J.4), about 2.5K characters a page. No hash moves, but what the AI reads changes, so it's off until a test (D120).

## Reference pages (2a, D54, D55)

- `stangent spec pages`: every page the graph calls for.
  - **Screens:** one per frontend route, id `page:<route>`; a server-rendered action (GET, returns `View(…)`) is a screen too.
  - **Shared components:** a component in 3 or more screens' slices gets its own page; screens link to it, not into it.
  - **Backend pages:** every endpoint (screens stop at the endpoints they call) and every event or command handler.
    Id: the entry point's graph id. Files: `specs/reference/{screens,components,backend/<project>}/<name>-<hash6>.{json,md}`.
- **The slice** (D54): the walk forward from the entry point, along the lines a change travels, to `spec.depth` lines
  (`spec.backendDepth` from an endpoint or handler). Side effects one step back: handlers of events it publishes,
  tables it maps to. A point with `spec.hubCallers` or more callers is included but not walked into. ❓ blind spots in
  the slice are appended to the page by code. Settings and defaults:
  `spec: { depth: 6, backendDepth: 4, splitAtEndpoints: true, hubCallers: 10, maxBundleChars: 260000 }`.
- **The bundle** (`stangent spec bundle <page>` prints it, without the previous version): instructions, schema, the slice's symbols with ✅/🟡, key
  lines, the source of each method and component, what it couldn't see, and the page's previous version. Its input
  hash covers everything but the previous version. Over `maxBundleChars` → listed as failed, never cut.
- **The writer** (`stangent-page-writer`) returns sections `shows`, `actions` (with the `endpoints` they call), `rules`
  and `sideEffects`; every statement cites symbol ids. Code gives them ids S1…, A1…, R1…, E1…. While a run is under way, the writer and the verifier see
  them numbered by place, as before; the permanent ids go on when the page is recorded.
- **Statement ids (2.3, D118)** stay with their statements. A page's ids at adoption become permanent, so nothing already cited moves. Each page has a ledger beside it, `<path>.ids.json`
  (`docs/foundation.md`). When a page is recorded again, code matches by exact signals, with no score:

  | The new statement | Its id |
  |---|---|
  | The same words, whitespace normalised, in any section | Kept. An id's letter says where the statement began. Repeated words pair off in order, the same section first. |
  | Other words, the same section, exactly the same cited symbols, alone on both sides among what's left | Kept. Its text changed, so a decision made on it drops back (`decided_on`, below), even when a quote still fits. |
  | Anything else | The next unused number in its letter. |

  An old id nothing claimed is marked removed in the ledger and never comes back. A link citing it isn't re-pointed: its statement is gone, so `trace check` lists it in `staleQuotes` and `retiredStatements`, and `--fix` drops its decision.
  A verifier's finding is recorded on its statement's final id, or `(removed in the fix)`.
- **Line citations (2.3, D118; `schemas/reference-lines.v1.json`):** code fills them from `graph where`, never the AI. `<path>.lines.json`, beside the page, gives each cited symbol its `file`, `start` and `end`,
  and the file gives the graph's `commit`. Nothing hashes that file, and it changes nothing in the page's JSON. The Markdown lists them under "Cited symbols".
  - Citations are per file, on `graph where`'s answer. A symbol in a dirty or untracked file, in a file the commit doesn't hold, or no longer in the graph, has `why` instead, and the page says so. Every other symbol keeps its citation. So does a symbol the graph holds only by file: it keeps `file`, with no lines and a `why`.
  - A graph with no commit, or one too old to say whether it was clean, writes no citation at all: the file's `note` says why, and so does the page.
  - A partial type's lines cover its first part only. Its `note` says so, in this file, on the page beside the citation, and on any evidence that copies the lines.
- **`stangent spec cite [page]`** fills citations for pages already recorded and adopts their ids. Code only, and it needs the graph, not the source. It doesn't touch a page's JSON, so nothing goes stale. It renders the Markdown again, and there a link goes only to a page that's recorded. It reports `citations` and distinct `symbols`, with and without lines, and `why`.
- **The verifier** (`stangent-page-verifier`, fresh context, bundle and finished page only) flags statements the slice
  doesn't support: `contradicted` (with the contradicting line, which code checks is in the slice: at least 12
  characters, and two tokens or a whole line (D103), so a fragment like `return` is no evidence; otherwise the finding is dropped) or
  `unsupported`. It gets one retry when its output is missing or breaks the schema. The writer then fixes or rejects each finding once; a "fixed" statement must
  change, a rejected `unsupported` finding needs the supporting line. Findings and outcomes are recorded on the page.
- **Recorded:** the page JSON (`schemas/reference-page.v1.json`) and its Markdown, rendered by code: the commit, the
  input hash, the slice size, the writer's and verifier's model, tokens, cost and time, and retries.
  `specs/reference/failed.json` lists pages that failed, with why; they're not retried until their inputs change
  (`--retry-failed` forces it).
- **Keeping current** (D55): `stangent spec stale [--diff base..head] [--format md]` lists pages whose input hash
  changed (with the changed files in each slice and the FSD sections linked to each), new pages and removed ones, as a
  PR comment. On merge, CI runs
  `spec-run.sh --stale` and opens a spec-only PR (see `plugin/ci/spec.yml`).

## Pages when they're needed (I.1, D131)

The normal way to make pages is for what needs them. On Sonarr 113 pages of 718 ever ran. `stangent spec needed --doc <doc> [--chapter N]` lists the unwritten pages that a document's sections have as candidates, with the sections each is for; `--ticket <key>` lists what that ticket's saved bundle says it's missing. `spec-run.sh --for-fsd <doc>` and `--for-ticket <key>` make just those. `--stale` now means written pages whose code changed: `--new` makes every page never written, and `--all` is every page, as before. A section with no candidate by code isn't counted: the candidate finder reads written pages' titles, so it can only name those. No prompt or hash moves.

## Only the statements a change touches (I.2, D131)

A changed line regenerates the whole page and its verifier. With `statement-update` on (off by default, because it changes what the writer gets), `<page>.shape.json` holds a hash of the code shown for each point in the slice. A stale page's statements whose cited points are all unchanged are kept by code: they go back on word for word, keep their ids, and the writer is told not to return them. The writer returns the rest, and anything new. The verifier reads only what isn't kept; if nothing is new it doesn't run. The input hash is the same either way, so saved pages stay valid. The writer still reads the whole bundle, because a new behaviour may be anywhere in it, so the saving is what it writes and what the verifier reads.

The whole page runs for a first version, a `page-wrong` mark, new instructions or slice settings, or no shape on file.

## Code that only moved (I.4, D131)

A page's input hash covers line numbers and file paths, so a line added above a method, or a C# file moved, makes the page stale, and a paid run writes the same thing. With `follow-moves` on, a page gets `<page>.shape.json` (contract `page-shape` v1): a hash of what it was written from with where the code sits left out, the same instructions and schema, points, lines and code. If that's unchanged, `spec prepare` moves the page on with no AI: its input hash, commit and citations change, and its statements don't. `spec stale` lists it under `moved`, not stale; `spec read` doesn't call it behind; `stangent spec follow` does them all at once and starts a shape for current pages that have none.

Anything else stays stale: a change inside the code shown, a new line in the graph, a change to the instructions. A TypeScript file that's renamed changes its symbols' ids, which hold the path, so it stays stale too, and the page runs. A page with no shape on file can't be compared, so it runs once. Off by default because it rewrites a saved hash. No number decides anything: the same or not.

## Navigation (T.7, D131)

A page's Markdown links to `specs/reference/index.md` at its top and bottom, and its footer says it's generated and how to correct it. The index lists every written page by kind and group; it's rewritten whenever a page is written, or by `stangent spec nav`. `stangent spec cite` puts the links on pages written earlier. Only people read these: no step reads a page's Markdown, so no prompt or hash moves.

## Every page accounted for (T.3, D131)

`stangent spec coverage` lists every screen, shared component and backend entry point the graph calls for, per kind: written, failed, not written yet, or excluded with a reason. `--strict` exits 1 if any is neither written nor excluded. A page not written yet isn't a fault in itself, since pages are made as needed (I.1): `--strict` is for a project that wants them all. It reports what the graph knows: what the graph can't see isn't here, and is counted where it was read (`docs/code-graph.md`).

`stangent spec exclude <page> --why "..." --by <name>` says a page isn't one, for a tooltip `root-screens` took for a screen, say. It goes in `specs/page-exclusions.json` (contract `page-exclusions` v1), and needs `page-exclusions` on. An excluded page isn't in `spec pages`, `spec stale` or a section's candidates, and nothing writes it. Other pages' slices and hashes don't move, because exclusions are taken off last. A page already written and then excluded shows as `removed` in `spec stale`, like any recorded page the graph no longer calls for. `spec include <page>` takes it back. An exclusion for a page the graph no longer calls for is listed as `gone`.

## A person's correction to a page (T.1, D131)

`page-wrong` asks for the page to be written again, and the writer may well write the same thing. A correction sticks. Off by default (`page-corrections`), because a corrected statement is what link judges then read, so those sections are judged again.

- `stangent spec correct <page> <statement> (--text "..." | --remove) --why "..." --by <name>` records it in `specs/page-corrections.json` (contract `page-corrections` v1), as `proposed`.
- `stangent spec correct-approve <C-id> --by <name>` is a person's yes. The page's JSON and Markdown say it from then on, marked in the Markdown. Its input hash doesn't move, so no AI run follows, and a `page-wrong` mark on that statement goes back to the person who made it.
- `stangent spec correct-reject <C-id> --by <name> --why "..."` refuses a proposal or withdraws an approved one. A withdrawn one is left off when the page is next written.
- Every time the page is written, code puts approved ones back on: by the statement's id, which stays with a statement (D118), then by the words it was given for. The writer isn't told, so no prompt or hash changes. If neither is on the page, it's `notApplied`, the step warns, and `spec corrections` shows it for a person. `codeMoved` there says the code changed since the approval.
- A correction changes or removes a statement. It can't add one: for something missing, `page-wrong` still applies. No AI anywhere in this: a person is the check (D18).

## Checks where pages are read and written (T.4, T.5, T.6, T.8, D126)

All code, no AI, and none changes a prompt or a saved hash.

- **`stangent spec read <page>`** (`--format md` for the page itself) prints a recorded page. When its inputs have moved on from the code, there's a warning on stderr, in the result, and on top of the Markdown. `spec ask`'s answer lists the same under `answer.pagesBehind`, and a ticket bundle has always had `stalePages`. A Markdown file opened directly can't warn: writing the warning into it would change it with every commit. `spec stale` in the PR comment covers that case.
- **`stangent spec content-check`,** run in CI. Broken: a Markdown link in a page to a file that isn't there, a link in `trace.yaml` to a page, statement or section that isn't there. Repeated: a page id, a statement id on a page, a section id in a document, a link id, an id in the requirements. A link to a page the graph calls for but no one has written is counted apart (`linksToPagesNotWritten`), since pages are made as needed. A retired statement and a removed section keep their links on purpose; `trace check` lists those. With no graph, a page not written yet counts as broken, and it warns.
- **`stangent run-check before|after --snapshot <file>`:** `spec-run.sh` and `ticket-run.sh` wrap each run in it. By git: the commit, and each changed or untracked file with a hash of its content, leaving out `.stangent/`, `specs/` and `stangent.yaml`. A change is `APP FILES CHANGED` on stderr and exit 1. It can't see git-ignored files such as build output, or say which job did it, and outside git it says it didn't check. A `--prove` run isn't checked: bug proof builds and runs the app (D75).
- **`plugin/scripts/read-only-hook.sh`** stops an analysis step writing outside `.stangent/` or running a command, through a `PreToolUse` hook. One-turn calls have no tools, so it matters for `--agents`, the file finder, and agents started through the plugin's commands, which `plugin/hooks/hooks.json` catches by their `agent_type`. The bug reproducer is the exception (D75). Only tested by feeding the script hook input: no real Claude Code has run it, and the `agent_type` field is as the assistant remembers it, not checked here.

## Asking how the app works (E.2, D124)

`stangent spec ask "<question>"`, or `/stangent:ask`, with `spec: { ask: true }`. Off by default. **It hasn't been shown to help, and no real AI has answered one.** It answers from pages, which are generated, so every answer is labelled `as the pages describe it`.

- **Code picks the pages,** by the question's words: most in a page's title or route, then most in its statements, then most statements holding one, then by id. The order of those is the rule, with no weights. A page holding none isn't picked. `spec.askMaxPages` (5, a stated setting) is the cap. No graph expansion.
- **The bundle** holds the question, those pages' statements with their ids, `page-asker.md` and `page-asker-output` v1.
- **`stangent-page-asker`,** one turn, no tools, as other AI steps are (D66). `spec-run.sh --ask "<question>"` runs it, printing a status line and the result as one JSON line. By hand: `spec ask`, then `spec ask-check "<question>"` with the same words.
- **The check, by code.** Every statement id has to exist on a page in the bundle, and every sentence has to cite one. One retry. The cited lines come from `reference-lines`, `path:lines` for each symbol the statement cites, and one with no lines says why, and `notCited` lists such statements. Nothing checks a sentence says what its statement says.
- **`answered` or `not-covered`.** An answer with no citations, or one that fails twice, is refused and says `The pages don't cover this.`, with `why`. A question no page holds a word of says it with no call. The same question on the same pages reuses the saved answer, with no call. Saved under `.stangent/spec-ask/`.

## The FSD (2b, D13, D16)

- `stangent fsd import <file> [--id <doc>] [--flat] [--accept-changes] [--allow-label <name>]` takes `.docx`, `.pdf`, `.xlsx` or `.xlsm` (D111, D123), by code only: the same file gives the same bytes, and
  what can't be brought in exactly is listed in `problems`, never dropped. `.xls` is `unsupported_format`, and says to save it as `.xlsx`.
- **`problems` are data (`source-document` v3, D121).** Each has `kind` (`comment`, `completeness`, `tracked-changes`, `flat`, `numbering`, `element`, `page-text`, `running-line`, `table`, `heading`, `contents`, `bookmark`, `image`, `other-direction`, `white-text`, `symbols`, `before-first-section`, `page-join`, `outside-body`, `attachment`, `hidden`, `shared-workbook`, `merged`, `formula`, `number-format`, `large-workbook`, `protected`, `not-read`, `sheet`, or `other`) and `detail`, the line a person reads, word for word what v1 and v2 held. Where the line says, it has `sectionNumber` and `section` (the permanent id, once known), `page` or `line`. A comment adds `author`, `state` (`open` or `resolved`) and `text`. Converters still write lines, and one reader, `ImportProblems`, takes them apart, for new imports and old documents alike. A line no rule knows is `other`, never dropped. v1 and v2 documents still load; the next import of the same file upgrades `document.json` and changes nothing else. A candidate's problems get their `section` when it's promoted.
- **The verdict and the report (D122).** Each import's result has `verdict`: `ok` with no problems, `ok-with-warnings` with any, `failed` when the file stopped (no_structure, no_text, a lock, a label, damage, unsettled changes), which is in the error envelope's `result`, since nothing was written. `specs/fsd/<doc>/import-report.md` is made by code from `document.json`: the verdict, the file, and the problems grouped by kind with counts, what didn't arrive (`completeness`) first. A candidate's is in `candidate/`, and promotion brings it over. `result.report` names it. No step reads it back, so it's in no hash.
- **Reading the original again (D122, A.1).** `stangent fsd reread <doc> [--allow-label <name>]` reads the archive's original with this build, so converter fixes reach earlier imports. The bytes must still hash to what's recorded (`archive_file_missing`, `archive_file_changed`). It compares text and section shape, not the file's hash. Different means a candidate through the flow below, `reread: true`, with the current version serving until a person promotes it. The same means `unchanged`; if the build has more to say, `problems` and the report are updated, `problemsChanged: true`, with no candidate, since problems are in no hash. A flat import stays flat, accepted tracked changes stay accepted and an allowed label stays allowed, with who allowed it. `candidate_waiting` refuses while another file's candidate waits.
- **Ids for tables and pictures (D122, A.6).** `document.json` has `tables` (`T-0001`, section, place in it, rows, columns, a hash of its text) and each picture has `id` (`F-0001`) and the first section that shows it, from the document's ledger. They're worked out from the text the conversion gave, so `document.md` and the sections don't change, and no hash reads them. A picture is its file, named by content. A table keeps its id by the same words in the same section, then the same words anywhere if unique, then the same place in the same section. An id nothing claims is marked removed and never comes back. An older document gets them on its next import, the same file included. Attachments have `A-` ids, below.
- **First-import approval (D122, A.9).** `components: { first-import-approval: true }`, off by default. A first import waits in `candidate/` with status `pending-approval` and no `document.json`, so nothing reads it, until a person runs `stangent fsd approve <doc>`; the name comes from git, and the move is on the state module. Only then does it get ids. `fsd discard` throws it away, another file replaces it, and `fsd promote` refuses it (`needs_approval`), as `fsd approve` refuses a new version (`not_pending_approval`). Stangent opens no PR and pushes nothing: if a team wants a spec-only PR around it, that's theirs.
- **The steps (D121).** `IImportFormat` in `src/Stangent.Spec/Fsd/ImportPipeline.cs` has safety checks, convert, comments, extract files and a completeness check; `ImportPipeline.Run` runs them in order, and the result's `steps` says what each did: `result` is `ran`, or `not-for-format` with why, so a missing step can't read as an empty one. Safety and convert can stop an import. Word and PDF read comments and check completeness in the walk that converts, so their steps report what it found; a PDF has `comments: not-for-format`, because its annotations aren't read. Excel fills in the same interface: its completeness check is a second pass reading each row back from the table.
- **`.docx`** converts with the Open XML SDK, in C#: headings (Word's automatic numbering worked out, numbers typed into headings, or
  plain), numbered and bulleted lists, tables, images with their captions. Inline formatting is dropped, because quotes are matched
  against this text. The same principle as a PDF: what can't be brought in exactly is listed in `problems`, by kind and section (D116).
  - **A number typed on a chapter heading** stays a number across a gap, because taking a chapter out leaves one, and `problems` says one is skipped. It's read as words, with a plain heading's id, when it's more than 10 past the chapter before (`2023 Roadmap`), when a lower-case word follows (`24 hour clock`), when a later chapter's number is at or below it (`3 Ways to pay` before `2 Pricing`), or when nothing numbered comes before it and the next number doesn't follow it. `1 Intro` then `3 Ways to pay` has the same shape as `1 Orders` then `3 Checkout`, so it reads as a number, and the skip is what tells a person.
  - **Tracked changes** (inserts, deletes, moves, including in a footnote, on a paragraph mark or a table row) stop the import: `docx_tracked_changes`, with a count, nothing written. The document isn't settled. Format changes don't count: they change no words. `--accept-changes` imports the accepted view: inserted text kept, deleted text gone, moved text once, a deleted paragraph mark joining the two paragraphs, as in Word. `problems` says how many were accepted. It's refused for a PDF. A re-import of a file already recorded stays `unchanged`, with or without the flag.
  - **Hidden text** (`w:vanish`, on a run or through a style, by Word's rule that a character style and a paragraph style cancel) is left out and listed with its word count, and so is a hidden table row. A hidden paragraph mark alone hides no words, only the line break, so its visible text stays, as its own paragraph, and is listed.
  - **Struck-through text** stays, listed, since a strike can mean a retired rule and only a person can tell.
  - **Comments** stay out of the text. Each is one `problems` item of kind `comment`, with `author`, `text` and `state` from Word's own resolved flag, in the order of their anchors. Its `detail` is the line `comment: section "4.2" by "Jane" open: "Is it 3 or 5?"`. One with no anchor left names no section.
  - **Footnotes and endnotes** come in at the end of their section, as `[Footnote 1, after "the last five words"] text`, numbered in reading order, which can differ from the number Word prints. The sentence itself gets no mark, because quotes are matched against it.
  - **Other things a file can hold:** a text box keeps its text where it's anchored, once, listed. SmartArt keeps its words as a list, listed, since its order isn't always the drawing's; in a table it's only listed. Embedded files (by program id, such as `Excel.Sheet.12`), charts, equations, symbols, ActiveX controls, old-style and linked pictures and `altChunk` documents aren't read, and are named with their section. A content control keeps its content, but a prompt still showing ("Click here to enter text") is left out and listed. A field keeps the text Word last saved, listed unless it's only a link, page number or contents. An `mc:Fallback` is a copy for old readers, skipped, only when an `mc:Choice` sits beside it; with none it's what the file holds, and it's read and checked. Page headers and footers aren't imported: one line with their word count.
  - **Tables:** a nested table keeps its words and is listed as flattened. A cell merged down rows repeats its value in each row, and is listed; text Word doesn't show in such a cell is left out and listed. A cell merged across columns keeps its value in the first column and blanks after it. A row that starts part-way across the grid keeps its cells under the right columns, and rows and cells inside a content control are read.
  - **Completeness check (D18), on every import:** the check reads the file apart from the converter, by element name in any namespace, every word in a text-bearing element. Per section, those words, minus what a rule removed, plus what the converter adds on purpose (numbers, list marks, table rules, footnote labels, repeated cells), must equal the words rendered in `document.md`. A mismatch adds a line, `completeness: section 4.2: 3 words in the file aren't in document.md ("…")`, and never fails the import, so a kind of element nobody thought of can't vanish silently. A word it can't see, such as text inside a picture, it can't check.
- **`.pdf`** reads with PdfPig. Principle: a false sentence is worse than a broken one, and a listed problem is better than either; when the code can't tell, it doesn't join and doesn't drop. The text is PdfPig's
  content-order extractor's, or its own rule run over only the letters read (below) when a page has others. Words are never changed (no de-hyphenation, no fixing).
  Wrapped lines join with single spaces. Paragraphs split on line spacing against the document's usual pitch, or where a line ends a sentence with room left for the next word; room alone proves nothing. A line after a list item joins it by the same rule, unless it starts with a marker of its own.
  A paragraph runs on over a page break only with strong evidence: the last line is body text at the body's size and left edge with no end mark, and the next page starts in lower case; never from or into a cell's paragraph or the text of a table kept as plain text. One `problems` line counts these joins, with their pages.
  - **What's read:** the page's main text direction, so a page turned as a whole reads normally. Text in other directions (watermarks, margin notes, diagram labels) is kept out of the text and listed once per pattern with its page count. Only what is certainly never painted is removed and listed per page with a word count: render mode 3 and text off the page, since a hidden rule mustn't read as agreed text. Invisible text over a full-page image is an OCR layer: kept, and listed as not checked. White text is kept and listed in one line, with its word count and pages, because whether anything dark lies behind it can't be told; a colour that can't be read counts as visible.
  - **Reading order, one rule:** the drawing order, unless it goes against position (back along a line, or up the page without moving wholly right to a new column). Then that
    page is read by position (columns, then top to bottom, left to right) and listed as order uncertain. Tables count: one takes its place by position, in the same order as the prose.
  - **Sections, in this order; fonts are never used to guess headings:** (1) bookmarks, depth giving the level; one with no page inside the document is listed and not used, its children still
    count. (2) The printed contents near the front: `title ..... page` lines, up to where page numbers fall (a list of tables or figures). An offset is worked out by code and **every** entry must then be a
    whole line on its page; level comes from the number's parts, an unnumbered entry is level 1, and `problems` says sections may be coarser than the real structure. (3) Otherwise, if any entry fails, or if more than one offset fits: `no_structure`, nothing written.
  - **Headings** must be a whole line, or whole wrapped lines; a line is never split to make one. The bookmark's position chooses between several matches; with no position the first is taken and listed as ambiguous.
    A title with no whole-line match is listed, its text stays as it is, and the heading goes where the page's remaining text starts. Text before the first heading is in no section (as for `.docx`), and for a PDF its word count is listed.
  - **Running headers and footers:** a line that stands apart from the text, at one distance from the top or bottom edge, on most pages (or most odd or even pages), and whose text is identical or differs only by a number following the
    page, Arabic or Roman. A number that doesn't track the page isn't a page number. A section's own title and lines inside a table grid never count. One `problems` line per pattern, as it reads, with its page count. A line that repeats but doesn't stand apart is kept and listed. A real rule that fits the pattern ("Day 6: the supplier must confirm…") is removed: it's listed, and only its content could tell.
  - **Tables** come from the page's drawn lines: a cell is a grid region closed on all four sides, and a merged cell keeps its place with blanks for the rest. A fill thicker than a rule is shading, not a line.
    Words are placed whole, by the baseline, never by a letter's glyph box, which some embedded fonts report wrongly. A grid that's seen and not emitted is listed (it frames the page, has no text, or has text in only one row or column). A lone row or column, or a grid with text in one row or column, keeps its cells' text apart in paragraphs, in the order drawn and apart from the prose around it, and is listed with its first words and shape, since its columns aren't kept; cells drawn line by line across a row alternate line by line. A single box round some text is prose. Other drawn lines that suggest a table are listed per page as a possible table: parallel rules a row apart with text between them, or a divider with text on both sides. A lone rule under one line of text is an underline and doesn't count; two or more with text between them always do, whatever their widths.
  - **Checks.** A table stands only if every cell is word for word (white space normalised) in the page's own text, no word or run of text crosses a rule, no word in the grid's drawn extent is outside a cell, and each cell's words are drawn in order; otherwise it's plain text and listed with the reason.
    Each page's read letters are also read a second way, by position with the extractor's own white-space rule; if the two readings give different words, the page is plain text and listed. The words emitted must equal the page's own, minus removed running lines; the plain-text fallback is checked too, and if that fails the page is its own lines, and listed.
    **The limit: every check rests on PdfPig's own letters, so none can catch altered letters. That would need a second PDF reader.**
  - **Images** are kept in reading position, named by content hash. One that can't be decoded is saved as raw bytes and listed. One `problems` line counts them: no AI or code reads them, and rules can sit inside diagrams.
  - **Symbols:** only clear bullets become `- `; a tick, an empty box or an empty circle stays as drawn, and a line starting with one starts a new line. Glyphs with no standard letter (a symbol font's private range, the replacement character) stay as drawn, with one `problems` line counting them, since quotes depend on them.
- **`--flat`** imports the whole document as one section, id and title `(whole document, no sections)`, with a `problems` line saying it has no structure. A re-import that changes
  between `--flat` and not is a changed import, so it comes in as a candidate (below).
- **Errors, with nothing written:** `no_structure` (a PDF with none of the above, or a `.docx` with no headings), `no_text` (no page has text), `pdf_locked` (any encryption, even one that opens without a password; protection is never worked around), `invalid_pdf` (PdfPig couldn't read the file, including an outline that loops or nests impossibly deep; usually damage, but it can be a valid file PdfPig can't handle), `invalid_docx` (damaged, or not really a Word file), `docx_locked` (a Word file with a password; it says how to get a copy that can be read), `document_labelled` (a sensitivity label nobody allowed), `docx_tracked_changes` (a Word file with tracked changes and no `--accept-changes`). A `.docx` with no headings lists, in the error's details, up to its first 20 bold-only lines of at most 15 words that don't end like a sentence, by paragraph, and says it never guesses (A.4).
- **Sensitivity labels (D122, A.3).** Word's `docProps/custom.xml` `MSIP_Label_*` properties and `docMetadata/LabelInfo.xml`, and the same properties in a PDF's information or XMP metadata. One switched off or removed doesn't count. Any other stops the import, with nothing written or archived, unless `--allow-label` names it by name or id. What was allowed goes in `labels` in the document's record, with `allowedBy` from git. Protection is never bypassed, and a label is never removed. A ticket attachment with a label isn't read, and `notConverted` says why. **Known gaps:** a label in another product's own property, or in XMP that doesn't parse, isn't seen, and a same-file re-import doesn't look again until `fsd reread`.
- **A table of contents (I.11)** is left out and listed: a content control Word marks as one, a `TOC` field across its paragraphs, or paragraphs in the `TOC1`–`TOC9` and `TOCHeading` styles. It's the headings and page numbers again, and it would land before the first heading as text. The style names are what Word writes in English; a table in a translated style outside a field or control stays in as text. Sonarr's FSD has none, and its `document.md` is byte-identical.
- **Known Word gaps:** never yet run on a file saved by Word itself, only on hand-built files and Sonarr's planted FSD, which a script wrote. A tracked merge of table cells (`w:cellMerge`) counts as a change but isn't applied. White text is kept and not listed. A style from a table doesn't count for hidden or struck text. A hidden run that splits a word leaves its two halves joined. A file imported before this check stays `unchanged`, with no new lines, until its bytes change. Ticket attachments, `.docx` and `.pdf` alike, go through the same steps (D121) and never stop the pull: the accepted view, flat when there's no structure, and `notConverted` when one can't be opened. `problems` and `format` stay in `ticket.json`, not in the bundle, which has no place for them. A PDF's `kind` stays `other`, since `ticket-bundle` has no other value for it.
- **Known PDF gaps:** a table split across pages stays as separate pieces; images are unread; no OCR, so a page with no text is listed and skipped; a title on a page doesn't prove it's the heading there. Fully borderless tables can't be detected without guessing: they flatten into text, unlisted. Tables ruled only across flatten into text too, and are listed; underlined lines close together are listed the same way, as a false alarm. Two columns drawn row by row can interleave. A word can split where PdfPig reads a gap in it. A capitalised sentence over a page break stays split, and a footnote at body size can join a lower-case next page (the join is listed). Near-white and fully transparent text is kept and not listed. Text covered by a shape isn't detected. Table rows drawn apart from each other lose their columns but keep their words in order. Text in another direction is listed with a page count, not its page numbers. Rotated column heads leave a table's header cells blank: their text is listed as another direction. A list item's label can read as a sentence's start, or the reverse, where nothing else marks a list. A page tree nested about 100,000 levels deep overflows PdfPig's stack as the file opens and ends the process (nothing is written): it can't be guarded before opening, and it takes a hostile file.
- **Excel (`.xlsx`, `.xlsm`; D123, A.5).** By code with the Open XML SDK. **No real Excel FSD has been seen:** everything here has run only on hand-built workbooks, none saved by Excel.
  - **Sections:** each visible worksheet is a level-1 section titled with its name, in workbook order, with a permanent id. Its `id` is the name (`idKind: path`). Headings inside a sheet are never guessed, and `--flat` is refused. A chart sheet, or a macro or dialog sheet, isn't a worksheet: it's named and has no section.
  - **Content:** one table per sheet, its first row the table's header because Markdown needs one, not because it's been judged a header. Empty outer rows and columns are trimmed; empty ones inside stay, as empty rows. A cell's line breaks become a space and a bar is `\|`. A merged range repeats its value in each cell and is listed; text under a merge, which Excel doesn't show, is left out and listed.
  - **Values:** what's stored. Shared strings and inline strings, numbers as stored (`1.10` stays `1.10`), `TRUE` and `FALSE`, error values as stored. Built-in date formats (14 to 17, 22, 27 to 36, 50 to 58) give an ISO date, and built-in times (18 to 21, 45, 47) a time, on the 1900 or 1904 calendar. A date Excel counts and no calendar has (day 60 of 1900) keeps its number and is listed. Other built-in formats show the raw number silently. A custom format shows the raw number and is listed by format, with a count and first cell, so a custom date format reads as its serial number. A formula shows its cached value and is listed with its text, once per shared or array range. One with no cached value is listed, shows empty and is never computed.
  - **Left out and listed (`hidden`):** hidden and `veryHidden` sheets, hidden rows and hidden columns, each with its count of cells holding text.
  - **Named, not read:** notes and threaded comments as `comment` problems, the shape a Word comment has, with the cell at the start of `text` (Excel's copy of a threaded comment for old readers isn't listed twice); charts, pictures, shapes with text, pivot tables, page headers and footers (`not-read`); external links, with their target; macros, by module name, from the project's OLE directory, never run.
  - **Stops:** `xlsx_locked` (a password; it says how to get a copy), `invalid_xlsx`, `no_text` (no visible sheet holds a cell with anything in it, whatever hidden sheets hold), `document_labelled` (as A.3, the same two places), `xlsx_too_large` (a sheet spanning more than 20,000,000 cells, merges included, or a file past the unpacking limits below), `xlsx_tracked_changes`. **A shared workbook's recorded revisions stop like tracked changes:** its cells already hold every revision, so `--accept-changes` reads them as saved and says so, and that answer holds for `fsd reread`. With a revision history that shows no change, there's no accepted state to compare, so it's listed (`shared-workbook`) and read as saved.
  - **Listed and readable:** a protected sheet or workbook structure (`protected`).
  - **Very large:** `fsd.excel.largeSheets` (50) and `fsd.excel.largeRows` (100000), `large-workbook` in the report. Stated settings, not measured, and it still imports.
  - **Completeness:** each stored cell is checked against the rendered table, read back row by row, or against a listed reason. A mismatch is a `completeness:` line.
- **Files inside a document (D123, A.6, A.7).** From `.docx` (`word/embeddings/`, packages and OLE objects), a worksheet's parts and files attached to a PDF. Each gets a permanent `A-` id from the document's ledger, and what it came to goes under `specs/fsd/<doc>/attachments/<A-id>/`. The file as it came goes to the archive (I.7, D16), at `<doc>/attachments/<hash 12>-<name>`, and its entry under `files` says where in `archived`, keeping the same `file` and `hash`. So does one nested at any depth. A document imported before this keeps its `original/` in the repo until `fsd reread`. `document.json`'s `attachments` holds each one's `fileName`, `from`, `hash`, `bytes`, `kind`, `reading`, `why`, `section`, `sectionNumber`, `chars`, `files` and `problems`; its section lists it in `attachments`, with a generated line in `attachmentLines`, shown by `fsd show`. **`document.md` and `text` don't change.** The report has a section for them, and each has an `attachment` problem, so a document holding one reads `ok-with-warnings`.
  - **What it comes to:** Excel gives one CSV per sheet, whose line N is row N of the sheet (a hidden row is an empty line; hidden sheets and columns are left out and listed in `problems`). Word and PDF give Markdown through the same import steps. A zip is unpacked and each file read the same way. A part's name can be anything, so one that says nothing goes by what it holds. An OLE object gives up the file in its `Ole10Native` or `Package` stream. Everything else is kept and listed, with why: other formats, `.xls` and `.doc`, a locked file, a scanned PDF, damage. PowerPoint isn't decided, so it's kept and listed.
  - **It never stops the import.** `reading` is `converted`, `kept`, or `withheld` for a sensitivity label nobody allowed: that file isn't copied into the repo at all (the archived original still holds it), and `--allow-label` applies to it as to the document.
  - **A file attached to a PDF has no section:** the PDF names no place in its text for one, and none is guessed. A change to one shows under `attachmentsWithNoSection` in the diff, since it's in no section's hash. The same goes for a file nothing in a Word body points to, and one on a hidden sheet.
  - **Giving those a home (`fsd.attachmentHome`, `attachment-home`, I.8, off by default).** On, they get one section at the end of the document, "Files attached to this document", made by code, numbered next if the document numbers its sections. Links and checks can then reach them, and a change to one changes that section's hash. A flat document's one section is their home instead, and no section is added. Off, nothing changes. It's off because a document with such files gains text and a section, which would mean paying to run it again. No real PDF with an attached file has been through it.
  - **Hostile input, by stated limits (`ImportLimits`), refused and listed:** a zip name that climbs out, is absolute, has a drive letter or a control character, or runs over 200 characters; a symbolic link; more than 10,000 entries; one file over 256 MB; 1 GB in all for one attachment, across everything nested in it; over 500 times its packed size past 10 MB; more than 3 files deep. Bytes are counted as they unpack, not read from a header. Writing checks once more that each path stays inside its folder. Each `.docx`, `.xlsx` and main workbook is put through the same unpacking check before it's opened.
  - **Ids** keep the same bytes in the same section, then the same bytes anywhere if unique, then the same name in the same section, since an edited file is still that file. Anything else is new; an id nothing claims is marked removed and never comes back. A candidate's files wait under `candidate/attachments/pending-0001/` and take their ids at promotion, when the old ones go.
  - **The client-data check.** `stangent data check` flags a tracked `.xlsx`, `.docx` or `.pdf` anywhere, on purpose. An import no longer leaves any `original/` in the repo (I.7). What it can still flag: one from before this, and a file nested in an archive that was kept and not read, under another path.
  - **Attachments in the checks (`fsd.attachmentsInChecks`, `attachments-in-checks`, off by default).** Off, nothing in a bundle or hash changes, with a test holding it. On, the link judge's, requirement judge's, agree checker's and disprove step's bundles add each attachment's text after the section's, a CSV as rows with bars, under `# This section's attachments`. The candidate finder's doesn't. Code's quote check accepts a quote from the section or an attachment, and the link records where in `fsd`: `attachment`, `attachmentFile`, and for a workbook `attachmentSheet` and `attachmentRow`. The section's own text wins. `trace check` checks the quote against that file, with the switch on or off, looked up in the document's record so a hand edit can't name a path, and keeps the row current. An attachment over `fsd.attachmentChars` (40000, a stated setting) stays out whole: the bundle says "not checked", and so does the report, from the setting at import. A finding's `document` citation names `attachment`, `file`, `sheet` and `row` (`evidence` v2). On promotion with the switch on, a changed file means the section runs again.
  - **Known gaps:** only hand-built files, never one saved by Word or Excel. A hostile PDF can still end the process as it opens (the page tree above), and now one inside a document can too: it can't be guarded before opening. Macros are named from stream names only. An old `oleObject*.bin` with no package in it is kept, not read. A plain `.csv` or `.txt` inside a document is kept and not read, as the owner listed the formats to convert.
- **Fingerprint (D123, A.8).** Each section keeps `textHash` and gains `contentHash`, over its text and its attachments' hashes; with none it's equal to `textHash`. An older document has none: it still loads, and matching falls back on the text.
- **Section ids:** the FSD's own number (`4.2.3`), or the heading path (`Calendar / Views`) where a section has none.
  Duplicate, missing and skipped numbers are reported in `problems`, never guessed. In a PDF, a parent with no number (`Chapter 7: Title`) doesn't stop
  its children keeping theirs (`7.1`), and a number out of step with its parent (`8.3.2` under `8.2`) keeps its id with a problem.
- **Links hold them too (D121, `trace-links` v4):** a link's `fsd.sectionId` is its section's permanent id, beside `section`, the number. `trace check` fills and corrects it, even without `--fix`, from `document.json`, where a section's number meets its id (`ids.json` only lists ids). The number stays, because entry ids and saved hashes are built from it; no hash reads `sectionId`. Promotion carries it, and `carried.sectionIdsDisagree` lists an entry whose number and id named different sections. A marked-removed entry keeps the id its mark holds. A feature has `sectionId` too, from when it's built, or the next `req prepare`.
- **Permanent ids (D117, `source-document` v2):** each section also has `permanentId`, `S-0001`, from `specs/fsd/<doc>/ids.json`. It stays with the section across versions and is never given twice. `id` stays as it was, because saved input hashes and link ids are built from it. A document imported earlier gets its ids on its next import, the same file included: it stays `unchanged`, the result says `permanentIdsAdded`, and only those fields change.

### A hand edit to `document.md` (D131)

Nothing reads `document.md` for its sections: every step reads `document.json`. So `fsd status`, `fsd outline`, `fsd show` and `fsd export` compare it with the import, section by section, and warn on stderr when they differ; `status` and `outline` also carry `documentEdited` in their result. Change the FSD and import it again. Text above the first heading has no section, so it isn't compared.

### Ranking doubtful matches (I.6, D131)

Each doubtful section in `fsd diff` also has `suggestions`: the unmatched sections on the other side, closest first, by the share of words they have in common, with the figure beside each. It only gives a person an order to read in. There's no cut-off, every section sharing a word is listed, and nothing reads it to settle a match: `fsd resolve` is still the only way.

### Where a document stands (D122, E.1)

`stangent fsd status <doc>`, or `/stangent:fsd-status`, by code, writing nothing: `current` (hash, title, sections, verdict), `candidate` (hash, state, whether it's a first import), `doubtful`, `coverage` (below), `queues` by who they wait on (`ba`, `agreeLinksToApprove`, `developer`, `developerConfirm`, `pageOwner`, with counts of `recheck`, `gone`, `closed`, `decided`), and `next`: who, what, and the exact command. A waiting candidate comes first, because nothing else is worth deciding on words about to change; then uncovered sections, the BA, developers, page owners and approvals. `next.who` is `nobody` when nothing waits.

### Reading a document (D122)

- `stangent fsd outline <doc> [--format text]`: each section's level, permanent id, number, title and size in words and lines, with `chapter` on each top-level heading, its place in the list.
- `stangent fsd claims <doc> [--section <number or permanent id>] [--format text]`: see [Claims in a section](#claims-in-a-section-d143).
- `stangent fsd show <doc> <section> [--format text]`: that section's text, by permanent id, number or heading path, with its `tables` and `figures` ids, and its `attachments` and generated `attachmentLines`.
- `stangent fsd export <doc> [--out <dir>] [--max-lines N]` writes one Markdown file per top-level heading, into `.stangent/fsd/<doc>/export/` by default. Git ignores that folder only where the repo's `.gitignore` lists it. `stangent init` adds the line, so a clone set up any other way shows `.stangent/` as untracked, and nothing adds it later. `ignoredByGit` in the result says whether the folder is ignored, for any folder. The limit is `fsd.exportMaxLines` in `stangent.yaml`, 1500 by default, a stated setting and not a measured one. A chapter over it is cut at its next heading level and so on down: `01-00-s0001-rules.md` holds the text before its first sub-heading, `01-01-s0002-pay.md` the first sub-heading. One section over it with no sub-heading stays whole, and is in `overLimit`. Text before the first heading is `00-front-matter.md`. Each file's first line says it's generated, is never read back and names the source's hash. Empty sections keep their heading. The same document gives the same bytes. An export removes only what an earlier export wrote, by that first line. A test holds that nothing in `src/` reads these files.

### Claims in a section (D143)

`stangent fsd claims <doc> [--section <number or permanent id>] [--format text]` cuts a section's text into claims by code, with no AI. It reads and prints, and writes only the telemetry event, unless `claim-links` is on ([below](#claim-ids-and-links-by-ids-d145)). Off by default (`fsd-claims`): off, it says `split: false` and that it isn't a pass. Nothing else reads claims yet, so no link, hash or bundle moves; ids and the judge come in a later slice.

- **A claim** is a `sentence`, a `list-item`, a `table-row`, a `step` (a numbered step inside a cell), a `flow-label`, a `figure` or a `block`. It has `section` (the permanent id), `position` from 1, `kind`, `words` and `flow`. A row's cells keep ` | ` between them. Steps stay in the order written, even where their numbers alternate between columns.
- **`flow`** is the nearest earlier text that introduces a set of steps, found from where cells sit and never from what they say. In `| Other paths: | Bad input. |`, then `|  | Person | Server |`, then `|  | 1. Press save. | 2. Refuse it. |`, each step's flow is `Other paths: Bad input.`. A first column labels steps that leave it empty, on its own row or above them. A row with one value labels them when it sits in the column they start in. Outside a table, it's a paragraph ending in a colon or all bold, directly before a list or a table of steps.
- **`notClean` lists what isn't clean,** with `notCleanCount` and `notCleanByReason`. Nothing is dropped, and code doesn't guess:

| Reason | What it means |
|---|---|
| `ends-open` | The last step in a cell ends with no stop, so it may go on in the next row. |
| `starts-mid-step` | A cell's text before its first number, so it may be the end of a step above. |
| `continues-above` | A paragraph or a one-value row starting in lower case, or one value between column headings and their steps. It keeps the flow and is never a label. |
| `numbers-out-of-order` | A cell's numbers don't rise, so it stays whole. |
| `maybe-sentence-end` | A stop before a digit, or after one letter or an abbreviation before a capital, wasn't cut. |
| `code-block`, `no-table-rule`, `row-not-closed` | Stays whole. |

- **The words check (D18).** The section's words are read straight from its text, with table rules, cell bars and list bullets aside, and compared in order with the claims' words. A difference is in `mismatches`, with `mismatchCount`, and the command exits 1 with the report in `result`.
- **`--format text`** prints `flow | words`, one a line, with `-` for no flow and `[reason]` after a claim that isn't clean. A whole document also has a `#` line for each section.

**A step a page break cut in two is one claim (D146).** A step with no end stop at the end of its cell joins the next row's text in the same column, when that text has no number before it and starts in lower case. It goes by position and punctuation, with no words and no tuned number, and the import doesn't change. It's strict: every such start in that row has to sit under an open step, a row of plain values joins only if all its cells do, and a row that labels a flow never does. Anything else stays apart and keeps its tags. A joined claim that still has no end stop stays `ends-open`. Text pushed out of the table into a paragraph isn't reached, and stays `continues-above`.

**The words check still reads the section's words in order.** A joined claim's second part may not sit next to its first: other columns can come between. The claim records where that part starts in its words and which claim it follows in the section, and the check reads it back there, so a moved, lost or changed word still fails. `claims.json` holds the joined words only. A joined claim's `C-` id is new, and the two old ones are retired, as with any change in words (none is in real use, since the switch is off). `fsd claims` adds `joinedCount`, `joined` on a claim, and `[joined]` in text.

### Claim ids and links by ids (D145)

Off unless `components.claim-links` and `components.fsd-claims` are both on. With either off, `ids.json` and every other file stay byte-identical, no input hash moves, and `TraceFile.EntryId` gives what it always did. Nothing here has run on a real AI.

- **Written by** `fsd prepare`, and by `fsd claims`, which then also prints each claim's `id` and `judgeKind` and an `ids` block of counts. From `document.json` alone, so no new import is needed. Twice in a row changes no byte.
- **`specs/fsd/<doc>/claims.json`** (`fsd-claims` v1): `id`, `section` (permanent), `position`, `flow`, `kind`, `shape`, `words`, and `problem` when there is one. Ids are in the `claims` scope of `ids.json`. The same section, normalised words and flow, and among exact repeats their order, keep an id. Anything else is new, and an old one is retired for good.
- **`kind`:** `claim` is judged. Set aside by where they sit: `column-heading`, `label-row`, `flow-label`, `figure`. What position can't settle stays a claim. `shape` is D143's kind: sentence, list item, table row and so on.
- **The judge's input** (`link-judge-claims.md`, or `-finer` with finer verdicts): the section's permanent id and title, its flows named once, then one line per set of repeated words with its ids and flows. Then the headings and labels for context, and the pages as ever. The section's text isn't there, and neither is an attachment's. A number isn't there either, so a section that only moved keeps its paid links.
- **The judge's output:** `links[]`, each with `state`, `note`, and `claims`, `page`, `statement` as the state needs (`covered` and `missing` for `partial`). Naming any id of a line answers the whole line. A flow that differs gets its own link, and ids of the line nobody named take the line's first answer. An unlisted id, or two states for one claim and one statement, take the one retry.
- **Entries:** one per claim a link answers, with `fsd.claim`, `fsd.quote` (the claim's words) and `page.quote` (the statement's whole text), both filled by code. The id comes from state, doc, section's permanent id, page, claim and statement. A judge's `undocumented` link has `fsd.claim: none`. The second check reads one line per link, and whatever words it copies when it raises a finding are ignored. The disprove step reads the entries as they are.
- **`trace check`** checks an entry with `fsd.claim`, switch on or off: the claim exists in its section, the quote is its words, the section's text cut now holds them, and `page.quote` is the statement's text. Never given out is a problem. Retired, or changed, is stale and the decision drops; retired ones are listed in `retiredClaims`.
- **Rulings from before** move when a section is next judged, not when the switch goes on. An old entry with a person's word on it carries to the new entries with the same state, page and statement, whose claim's words hold its FSD quote at word edges and whose statement holds its page quote. It goes to every flow with those words, marked `carried_from`, with an `id-moved` history line, and the `X-` id, grade and evidence go to the first. Ambiguous or unmatched goes `gone`, and with this switch on so does a decided `agree` link.
- **`fsd check`** adds `unanswered` (`id`, `flow`, `words`) and `unansweredCount`, and the run keeps `unansweredClaims`. It never fails a section in this slice.
- **Repeats:** a judge's line holds claims with the same normalised words, a leading step number aside (D146), so "3. It confirms" and "4. It confirms" are one line. A line whose numbers differ shows the words without one. Each claim keeps its own words, id and quote.
- **Stays as it was:** a section whose requirements are built keeps its requirement judge. `group-sections` doesn't group while this is on.

### Workflow files (D144, D147)

`stangent workflows <doc>` writes one readable file per flow, by code with no AI. Off unless `components.workflow-files` is on, which needs `claim-links` (and so `fsd-claims`); off, it says `written: false` and writes nothing. A `claims.json` that isn't the document's now is refused, `claims_out_of_step`: run `fsd claims <doc>`.

```
specs/workflows/<doc>/index.md                     one line per section with flows: "Login: 6 of 8 flows match"
specs/workflows/<doc>/s-0120-login/c-2474-main-sequence-of-events.md
```

- **Holds no fact of its own.** Words are filled in from `claims.json` and the page's JSON when it's written. Nothing reads these files, with a test holding that, and they're in no input hash. Each file's first line says it's generated and not to edit it. The same inputs give the same bytes.
- **What goes in:** sections whose claims of kind `claim` carry a flow. Everything else is counted in `index.md`: sections with none, claims in those sections with no flow, flow labels with no steps, and links on no step. "Use case" here means a section with flows.
- **A step shows** its words, claim id and state, a `cut:` tag if it has a problem, and for each link its state, page, statement id and words. A finding adds its `X-` id, the disprove verdict, the person's decision and who it's with.
- **Order:** by the steps' own numbers when every step has one and none repeats; otherwise as in `claims.json`. A joined or repeated step appears as it is there, and a step in several flows is a claim in each.
- **Names:** the section's `S-` id and the flow's label claim id (its first step's if it has no label), each with a slug, so a new section number renames nothing and two flows with the same words can't collide.
- **A rebuild** removes only files that start with the generated line, only in this folder, then folders left empty.

**A step's state**, the first that applies across its links. A `gone` finding is shown and counts for nothing.

| State | When |
|---|---|
| `differs` | Ruled `code-wrong`, `fsd-wrong` or `accepted`, or an undecided conflict with the verdict `stands` |
| `open` | A finding waiting on a person, including a refuted or unreachable one nobody confirmed (D119), `page-wrong`, `defer`, or a disputed agree link |
| `agree` | An agree link. An `unclear` finding beside it leaves it `agree` and is counted as an open question |
| `closed` | A finding closed as not real: `not-a-difference`, `agree`, or a confirmed `refuted` or `unreachable` |
| `open` | Only an `unclear` finding |
| `not answered` / `not judged` | No link, in a section with or without links by claim |

**A flow's status**, the first that applies:

| Status | When |
|---|---|
| `not judged` | No link on the section names a claim, including a section with only older links by quote |
| `differs` | A step differs |
| `open` | A step is open |
| `not answered` | A step has no link |
| `matches` | Every step is `agree` or `closed` |

The heading also counts open questions: every link waiting on a person, whatever the status.

### A new version (D117)

A first import goes straight in, unless `first-import-approval` is on (above). The same file again is `unchanged`; if a candidate is waiting it gives its hash in `candidate`, and a `note` says promoting would still apply it and how to discard it. A different file for that document id no longer replaces it:

- **It waits.** `specs/fsd/<doc>/candidate/` holds its `document.md`, images, `pending.json` (its record, ids still to come), `section-diff.json` and `SECTION_DIFF.md`. The current version keeps serving everything until promotion. The same file again is `waiting` and keeps what was settled; a newer file replaces the candidate and starts over.
- **Matching, by code, in order, on the section model, so `.docx` and `.pdf` alike.** A heading path is the titles from the top down, without numbers. "Unique" means in the whole document, on both sides.

| Outcome | Rule |
|---|---|
| `unchanged` | The same body and heading path, as a unique pair. Its number may change; `numberChanged` says so. |
| `moved`, `renamed` | The same body, unique and not empty. `renamed` is a new title under the same parent; anything else is `moved`. |
| `modified` | The same heading path, unique, with another body. Also the same body and path with other attachments: `attachmentsChanged` names each file and `changed`, `added` or `removed`. Moved and renamed sections keep their outcome and say the same. |
| `doubtful` | Anything left that shares a whole sentence with any section on the other side, listed with those candidates and marked `alreadyMatched` where they are. Also anything left with the same heading path as a section left on the other side, so a rewrite under a repeated heading never sets an id aside silently: that candidate has `sameHeading: true` and no `sentence`. |
| `added`, `removed` | Left, with no shared sentence and no such heading. |

  A sentence is one from `Sentences.Of`, with whitespace normalised and table rows counted, holding at least 4 words: "See above." says nothing about where a section went. There's no score and no threshold. A split or a merge lands in `doubtful`, on both sides.

  **`split` (I.5).** A doubtful section of the current version whose sentences went to two or more candidate sections, each of which shares sentences with no other section, also has `splitInto`, and each part `splitFrom`. Counts and `SECTION_DIFF.md` show it on its own line and under its own heading. It stays `doubtful`, in that count too, and `promote` still waits: at most one part can keep the id and the links, and that's a person's call (D15). A merge is still plain `doubtful`.
- `stangent fsd diff <doc> [--format md]` shows the diff. `no_candidate` (exit 3) when none is waiting.
- `stangent fsd resolve <doc> <candidate-section> --same-as <S-id>` or `--new` settles a section in the candidate. `stangent fsd resolve <doc> <S-id> --removed` settles one in the current version, for a merge. `--same-as` also settles the id it claims. Who decided comes from `git config user.name`, never an option; with none set it stops with `no_git_identity`. Refusals: `not_doubtful`, `section_id_taken`, `section_id_removed` (a removed id never comes back), `not_found`. A person can change their mind, and the id they let go of goes back to doubtful.
- `stangent fsd promote <doc>` refuses with `doubtful_sections_remain` (exit 1), listing them, while any are open. `candidate_out_of_date` if the current version isn't the one compared. Otherwise the candidate becomes current: settled and exact matches keep their ids, the rest get new ones, ids nothing claimed are marked removed, and `candidate/` goes. `promotions.jsonl` keeps a line per promotion.
- `stangent fsd discard <doc>` throws the waiting candidate away, by a person whose name comes from git, with a line in the history. The current version never changed, so nothing else does, and the file can come back as a candidate. `no_candidate` (exit 3) when none is waiting.
- **What follows a section, by code, with no file changing shape.** Trace entries get the new number and title, and a new `id` because it's the hash of the link, with the decision and `decided_by` kept. Feature files, every quote, and questions follow; a feature goes under its new parent's. Run keys move. A run's `inputs` is worked out again only when it was valid for the old section and only the number changed, so a renumbering costs no paid run; `carried.runAgain` lists the sections whose words changed. `carried.traceIds` holds old and new entry ids.
- **A modified section** then goes through the existing drop-back (D58): promotion runs `trace check --fix`, and `staleQuotes` lists what dropped. Its requirements rebuild at the next `req prepare`, as they do whenever a section's text changes.
- **A removed section** is listed in `carried.removed`: its trace entries, features, requirements and questions. Nothing is dropped. Its features and questions move to the section `(removed S-0007) 3.2`, so a new section given that number can't pick them up. Its trace entries take the same mark, and a new `id` because it's the hash of the link, in `carried.traceIds`. Their title, decision and `decided_by` stay, with no move in the history; `carried.removed[].decisions` lists what they hold. `trace check` flags them until a person deals with them, and its fix leaves them alone, since there's no section to compare a quote with. A screen whose only link is on a removed section counts as undocumented, a draft leaves that section out, and impact answers and stale-page lists show the mark.
- History: a moved entry's new id gets an `id-moved` line in `specs/trace-history.jsonl`, so `state history` shows what happened under the old id. Its `X-` id never changes.
- CI: `TraceCheck` and `trace attribute` look up a moved entry in the base file by its link without the section, so promoting doesn't read as a typed `decided_by` or a new decision.
- **Known gaps:** see `phases/2b-fsd.md`. No real document with two versions has been through this yet (D56).

- The original goes to the archive set in `stangent.yaml` (`fsd: { archive: { name, path, git } }`, a folder outside
  the repo or a second git repo, which gets a commit) and is cited by archive name, path and content hash.
  A file with a known hash is imported once.

## Links, findings and decisions (2b, D53, D58, D62)

Each step here has a switch (D121, `docs/foundation.md`): `candidate-finder`, `agree-checker`, `requirements-links`, `findings`, `disprove`, `line-citations`.


- `stangent fsd candidates`: candidate pages per section, by code: section titles ↔ routes, component names and page

  titles only.
  With `shared-through` on (off by default, because it changes what a judge reads, D140), a candidate screen also brings the
  shared components it reaches through its unshared ones, `why` saying `shared component reached from <screen>`. It stops at the
  first shared component on each path, which is what the screen's page links to, so one's own subtree isn't walked. It works for any screen with a
  slice, so a no-route screen (`root-screens`) and a `render=` route (`route-render`) too. A shared component's name still finds
  its own page as before. No new limit: what's already found stays first, the nearest come next, and the rest fits within

  judged again; with it off, every bundle and hash stays the same. Untested with a real AI.
- `stangent fsd prepare|check <doc> <section>`: `stangent-link-judge` (fresh context) returns links — `agree`,
  `conflict`, `gap`, `undocumented`, and `partial` and `unclear` with a switch on (below) — each quoting the FSD sentence and the page statement exactly. Code checks both
  quotes word for word, both ends exist, and every symbol the quoted statement cites is in the graph. Every `agree`
  then goes to `stangent-agree-checker`, a second fresh check: `confirmed`, or `disputed` and turned into the finding it
  raises. `specs/trace-runs.json` records each section's inputs, candidates (by code or AI), tokens and retries.
- `stangent fsd undocumented`: screens no section links to are undocumented, by code, within `fsd.scope`: the areas

- **Findings are off by default (D68):** with `fsd: { findings: false }` (the default) sections record only links;

  on (the Sonarr benchmark does); changing it makes each section run again.
- **`specs/trace.yaml`**: one entry per link or finding; people edit only `decision` (`agree`, `code-wrong`,

  under a chapter in one edit. `stangent trace check [--base <ref>] [--fix]` is the CI check: schema, ids, both quotes
  still in the FSD and the page, the statement's text still what the decision was made on (otherwise the decision drops back to undecided), cited symbols, and `decided_by` never
  typed. After a merge, `stangent trace attribute --base <ref> --by <who>` fills `decided_by` and `severity_by` from the code host. Every decision's and severity's move goes in `specs/trace-history.jsonl`.
- **`stangent trace links <doc> [--section <number>]`** shows every link of a document in file order: its state, finding, section and FSD sentence, its page statement, and the code lines that statement cites, with the line map's commit and counts. The lines come from the page's citations, looked up when you ask (D133), so they show where to look and don't prove the code matches: the AI compared the sentence with the page, not the code, which is what `codeFrom: "page-citations"` says. Where there are none, `codeNote` says why: `no page statement`, `statement not on the page`, `page has no line map` or `no code cited`. A citation of another page isn't a code line and is left out. It only reads: no AI and no project file changed, only the telemetry event every command writes.
- **What a decision rests on (D118):** `decided_on`, beside the decision, is the hash of the page statement's text, whitespace normalised. `trace approve` and `trace attribute` write it, and otherwise the first check does, so an old file gets one and drops nothing. If the text changes, even with the same id and a quote that still fits, a plain check lists a problem, and `--fix` drops the decision on the state module. Either way `changedStatements` and `counts.changedStatements` report it, apart from `staleQuotes`. The drop-back clears it, and a re-judged link carries it. Changing it by hand, against the base, is a problem. No input hash reads it.
- **`recheck` and `gone` (D122, C.3).** `standing`, by code on the state module (`finding-standing`), hashed like a verdict so a typed one counts for nothing and is a problem. Decisions drop exactly as before: this only adds what happened, for findings a person decided. It's `recheck` when a decision drops because a quote or statement changed (D58, D118) or a `page-wrong` page was written again (D119): `decision` is null, so no reader counts it and it goes back to the BA (D119's send-back still applies), and `standing_note` keeps what it was and who said so. A person deciding again clears it, at `trace attribute`. It's `gone` when a new build doesn't find a decided finding: the entry stays, with its `X-` id, kept and listed apart, in `gone` and the queue of that name rather than in `findings`, out of every reader's lists as a closed one is, and with its evidence as it was and nothing checked against it. If the same link comes back, the same id returns as `recheck`, never decided again by itself. A finding nobody decided that goes away is removed and its id retired, as before. `trace check` lists `standing`, `was`, `wasBy` and `standingWhy`, with `counts.recheck` and `counts.gone`. No hash reads any of it.
- **Section coverage (D122, C.1).** `trace check`'s `coverage`, per document: `linked` (an entry with a page), `notInCode`, `empty` (no text to check) and `uncovered`, with `counts.uncoveredSections`. It reports and never fails a check. A gap with no page doesn't count as a link. `stangent fsd not-in-code <doc> <section> [--why] [--clear]`, by permanent id or number, is a person's word, with the name from git, on the state module (`section-coverage`), in `specs/fsd/<doc>/not-in-code.json`. It follows the section across versions, and holds for the words it was made on: if the text changes, the section is `uncovered` again with `markWas`. A `notInCode` section lists its `attachments` (pictures by id, embedded files by name) so what sits in it is seen, and `alsoLinked` if it has links too.
- Impact answers reach FSD sections through the links (`impact-report` v5, `docs/code-graph.md`).
- **What a finding carries (2.4, D118, `trace-links` v3).** Code gives each `gap`, `conflict` and `undocumented` entry these on `trace check`, with or without `--fix`, and saves the file when it adds any. The AI never sees or writes them, and no input hash reads them, so an entry's id doesn't change. A file with no findings isn't touched. Files written by v1 and v2 still read.
  - **`finding`:** `X-0001`, permanent, per project, from `specs/trace-ids.json`. A re-run giving the same link keeps it, and so does a promotion that moves its section. One nothing holds any more is marked removed and never comes back. Used twice, or changed by hand against the base, it's a problem.
  - **`evidence`:** records of contract `evidence` v1, one line each, filled by code from what's known. `X-0001.fsd` holds the FSD quote and the document's `contentHash`, `stated`. `X-0001.page` holds the page, statement and quote, with the page's commit where it's a full one, `read`. `X-0001.code.N` holds each symbol the quoted statement cites, with `path:lines`, the commit and any `citation.note`, `read`, where the page has line citations; a dirty file gets none. All of it is derived again on every check, so it follows a page recorded again, and it's byte-stable when nothing changed. `evidence_hash` holds its hash as code wrote it. `checkedBy` is `trace check`, the judge's and second checker's models from `specs/trace-runs.json`, and the person who decided, only ever from `decided_by`. `ran` is never filled in here, because nothing here ran, and there's no way to add evidence by hand.
  - **Checks, in `problems`, as any other failure:** `EvidenceValidator`'s rules; a citation that doesn't match the finding's own quotes, document, page and statement; a code symbol not in the graph; the wrong strength for its kind; and evidence citing a finding (`X-…` or `trace.yaml`), since an opinion can't back up a claim about today's behaviour (D53). A record that's neither what code derives now nor what it wrote before (the base's copy with `--base`, otherwise `evidence_hash`) is refused by name, and `--fix` leaves it refused. Delete it, and code writes what's true.
  - **`severity`:** one scale, `Severity` in Core: `blocker` (users on the normal path lose data or can't finish), `major` (a wrong result on the normal path, or blocked on a rare one), `minor` (wrong on a rare path, or confusing), `cosmetic` (wording only), and `ungraded`, where code starts it. Code can't judge the effect on users, so a person sets it the way they set `decision`, by editing the file in a PR. `trace attribute` sees the change, moves `finding-severity` on the state module and fills `severity_by` from git. It's a field of its own, not `decided_by`, because a decision's drop-back clears `decided_by` and a grade stays. A typed `severity_by` is a problem, as a typed `decided_by` is. The disprove step can suggest a grade; it's shown beside it, and a person still sets it.
  - **Kept apart:** a page's statements come from the page's JSON only, and `specs/trace.yaml` isn't one of the things the page's writer, the verifier, the judge or a ticket bundle reads for a statement. A writer's citation must be in the graph, so it can't cite `X-0001`.
  - **Shown:** `trace check` lists each finding's `id`, `entry`, `state`, `severity`, `doc`, `section`, `page`, `statement` and `decision` in `findings`, with `counts.findings` and `counts.bySeverity`.

A symbol whose file differs from the commit isn't shown, and the bundle names it and says why.

Then what the page's other statements cite. Then the rest of the page's slice and the slices of the endpoints it reaches, because a screen's slice stops at the API (D63). Each group goes by how many of the claim's words a symbol holds, then smallest first. What doesn't fit is named.

That one stays `unverified`. A finding with no code to read gets `cant-tell` from code, with no call. A graph that can't say its tree was clean stops the run: `graph build` first.

A person's `decision` outranks all of it: `decided`, or `page-owner` on `page-wrong`. `suggestedSeverity` is listed beside `severity` and writes nothing.

The name comes from git, the move goes on the state module (`finding-review`), and `review_hash` ties it to the verdict, so a typed `review` closes nothing and is a problem. A new verdict starts with nobody's word on it. A confirmation drops, like a decision, when the statement or quote it was made on changes.
  - **A dropped decision (D119):** when `trace check --fix`, a regenerated `page-wrong` page or a person's PR takes a decision off a finding that has a verdict, the finding goes to `ba`, labelled with why. The old verdict doesn't take over, with `fsd.disprove` on or off. A later changed bundle still means a new verdict, which waits for a person the same way.
  - **On file:** `verdict`, moved only by code on the state module (`finding-verdict`); `disproof`, with the quote, the agent and the bundle's hash; `disproof_hash`, so a verdict typed by hand to clear a finding is a problem, on the same terms as `evidence_hash`. The quote becomes evidence record `X-0001.disprove`, `checkedBy` the agent and then the code check, derived again on every check like the rest.
  - **What the hash holds:** what the verdict rests on: the instructions, the document, the section's title and text, the claim, the page's statements, each symbol's path, name and code, what couldn't be shown, and the entry points. The bundle shows three more things it leaves out: the commit, the section's number and each symbol's line numbers. So a new commit, a moved section or code pushed down a few lines with the same words keeps the verdict and a person's confirmation, and costs no call. A verdict's `path:lines` are as of the commit it was given at, `disproof.commit`, which is on its evidence and listed as `atCommit`.
  - **Staying current:** an unchanged bundle means no call. When the bundle changed, the old verdict drops to `unverified` before the new call, so a closed finding reopens, for a person to look at again, even if the call never comes. Until the next `disprove prepare`, a verdict can be older than the code; `trace check` doesn't see that.
  - **Readers:** only a closed finding, one a person confirmed, leaves the ticket bundle, a draft's sections and impact's `fsdSections`. A `developer-confirm` or `page-gap` one stays in them, marked unconfirmed as before.
- **`page-wrong` (D119).** The BA says the reference is wrong, in a PR like any decision, with `decided_by` from git and `decided_on` as usual. The entry needs a page, or `trace check` says so. `spec stale` lists the page, with `reportedWrong` on the item, even though its inputs didn't change, so `spec-run.sh --stale` picks it up. `spec prepare` runs it, and the writer's bundle says what was reported, after the hashed part: the statement and the FSD's quote, or for a gap, that the page has no statement on it, with the quote. Writing the page again drops the decision back on the state module, so it returns to the BA. Impact's `verified` is false while it holds. Page steps don't depend on the links: `spec prepare`, `spec check` and `spec stale` read a broken `trace.yaml` as no marks, say so in `warning` or `traceProblem`, and carry on.

## Smaller disprove bundles (I.3, D131)

44 of 62 disprove bundles hit the 60K code cap. With `disprove-small` on (off by default, because it changes what the disprover reads, so its saved verdicts run again), a claim that cites code gets only what the page's statements cite. A gap, which cites nothing, gets those plus the slice's code that holds at least one of the claim's words, since that's where an omission shows. What's left out is named under "Couldn't be shown", so the agent knows. No new number: the 60K cap stays.

With `disprove-callers` on (D146, off by default, for the same reason), a finding whose page is an endpoint also gets the frontend code calling that endpoint, from the graph's `frontend-http` lines, straight after the claim's own cited symbols and under the same 60K. What doesn't fit is named under "Couldn't be shown" and counted in `withSomethingNotShown`, as ever. A line from another service isn't a frontend caller. It also adds instruction text (`finding-disprover-callers.md`): a claim about something the bundle doesn't hold, such as a colour, is `cant-tell`, not `refuted`. There's no CSS in the graph, so that's the whole answer for a stylesheet. Off, no text or hash moves. No AI has read this.

The risk is the agent not seeing what it needs and answering `cant-tell`, so it's watched: each verdict made this way carries `disproof.bundle: small`. `fsd disprove estimate` shows `small`, what the pending bundles would be this way, and `watch`, `cant-tell` among recorded verdicts, small and full apart. No AI to read either.

## The link judge's finer verdicts (C.4, D124)

`fsd: { judgeFinerVerdicts: true }`, off by default. **It hasn't been shown to help: no real AI has seen these prompts,** and whether they cut false alarms is what the paid re-score would say.

- **On,** the judge reads new instruction text (`link-judge-finer.md`, `requirement-judge-finer.md`) and answers with a new schema (`link-judge-finer-output` v1, `requirement-judge-finer-output` v1). The bundle differs, so the input hash does, and a section runs again. Off, nothing it reads has changed, and `SavedWorkTests` holds that.
- **`partial`** is a kind of finding: the statement covers part of the claim and leaves the rest unshown, with nothing that contradicts it. It needs both quotes, like a conflict, and `covered` and `missing`, kept as `partial` on the entry. It takes an `X-` id and goes to the disprove step when that's on, and through the queues as any finding.
- **`unclear`** needs the FSD's quote and a reason, in `note`, and names no page. It goes to the BA labelled `unclear, not counted as a difference: <reason>`, and takes an `X-` id so it can be decided. It isn't in `counts.findings` or `counts.bySeverity`, which is `counts.unclear`, and `difference` on the listing says false. It doesn't count a section as linked, or reach a ticket bundle, a draft or an impact answer, as it has no page, and it isn't sent to the disprove step. With `findings` off it isn't recorded, and the run says `unclearLeftOut`.
- **Readers.** A ticket bundle lists a `partial` link (`ticket-bundle` v2 grew in place, not being on `main`). A ticket match counts it as a link that shows the code. `impact-report` v5 is on `main` and has no such state, so an impact answer's `states` reads it as `conflict`.
- **The scorer.** A `partial` on a planted item counts as `found`, and not as `foundAsKind`. An `unclear` one counts as neither found nor noise. `finerVerdicts` reports both: the counts, which planted items a partial found, and the unclear entries.

## Judging small neighbouring sections together (C.6, D124)

`fsd: { groupSections: true }`, off by default, so a rule split across two sections is read as one. **Whether that helps is unknown: no real AI has read one of these bundles,** and turning it on on a real document re-runs every unit, which is paid.

- **The unit:** walking the sections in order, a run with the same parent and up to `fsd.groupMaxChars` (4000, a stated setting, not a measured one) of text between them. A section with no text ends a run. So does one over the limit, which is judged alone, and one judged by requirement (`requirements-links`), which already has its own unit. If code finds no page for the whole unit, each section takes the usual road alone, through the candidate finder.
- **The steps:** `fsd prepare <doc> <first section>` writes the bundle: all the sections, then the pages for all of them, with `link-judge.md` (or its finer variant) plus `link-judge-group.md`, and a schema of its own (`link-judge-group-output` v1, `link-judge-group-finer-output` v1). The others answer `grouped`, naming the first, with no call, so `spec-run.sh --fsd` needs no change. The candidate finder doesn't run. The agree checker reads the same sections.
- **Each link cites its own section.** `section` is required, code checks the FSD quote against that section alone, and one that names another unit's section is rejected. A link's entry is on its own section, with an id as usual.
- **`specs/trace-runs.json` records the unit,** as `unit` on each section: `kind`, `leader`, `sections`, `inputs`, `links` and the unit's usage.
- **Its own hash.** A unit's `inputs` are over its own bundle, and a section's own `inputs` aren't touched. `saved` beside them keeps what each side last gave: `own` and `group`, each with its inputs and its links, with no decision or finding fields. So turning it on re-runs; turning it off puts each section's saved links back with no call, once that section is prepared, as long as its own inputs are unchanged; and turning it on again does the same for the unit. A person's decision follows the rule it always has (D58, D122): the same link comes back with it, and one that didn't come back drops or goes `gone`.
- **Off,** nothing in `trace-runs.json`, any bundle or any hash changes.

## Comparing tables with the code (C.2, D124)

**A second route to code, off by default.** Everything else reaches code through pages. D68 kept direct links out as noisy, and that question is the owner's and still open, so this is labelled on every result and `fsd.compareTables` is off. **It hasn't been shown to help, and there's no real FSD on a C# project to pilot it on:** every test uses hand-built documents.

- **`stangent fsd tables <doc>`** lists each table with its `T-` id, each attachment's sheet with its `A-` id and sheet name, their columns and rows, and any attachment with no sheet to read. Code only, with or without the switch, so a person can write the map first.
- **`specs/fsd/<doc>/table-map.yaml`** (contract `table-map` v1), which a person writes or approves. An AI may propose one later; not now. `aliases` is where a name difference is declared, and nowhere else.

  ```yaml
  version: 1
  tables:
    - { table: T-0001, column: Field, kind: api-field, target: POST /api/orders response }
    - { table: T-0002, column: Status, kind: enum-member, target: OrderStatus, valueColumn: Code }
    - { table: A-0001, sheet: Fees, column: Tier, kind: enum-member, target: FeeTier }
  aliases:
    - { fsd: Customer Name, code: customerName }
  ```

- **Facts from the code.** `api-field`: the JSON fields the graph holds for a type an endpoint sends or receives, one level deep, by the type's name or graph id, or by `<VERB> <route> request` or `response`. A match says how many `maps-field` lines reach it as `frontendFields`. `enum-member`: from `.stangent/graph-enums.json` (`docs/code-graph.md`). **Not done:** constants and SQL seed data, which the result says under `notDone`.
- **`stangent fsd compare-tables <doc>`** applies the map, by code with no AI. A name matches in any case and nothing else, so `customer_name` against `customerName` needs an alias. For each line it gives `matches`, `differs`, `fsdOnly`, `codeOnly` and `skippedRows`. `differs` needs a value to compare, so today it's only an enum's `valueColumn`: the graph holds no value for an API field. `unmapped` lists every table no line names, and `attachmentsNotRead` every attachment with no sheet, so nothing is silently unchecked. A line it can't apply goes in `problems` and leaves what's on file from it as it was. With no map it says `noMap` and writes nothing.
- **Each difference is a finding of its own kind, `table-fact`,** in `specs/trace.yaml`, with `by: code` and what was compared in `table_fact`: `route: table-facts`, `result` (`differs`, `fsd-only`, `code-only`), the table, column, row, target and both values, and the code's `path`, `start`, `end` and `commit`. Its quote is the table's cell, or the column's header for a name only the code has. Its evidence is that cell, `stated` as every document citation is, and the code's lines, `read`; `table_fact.strength` is `read`. A file that may not match the commit gets `linesNot` and no lines.
- **Where it goes.** The BA's queue, with state and history like other findings, labelled by its route. Its own switch writes it, whether or not `fsd.findings` is on. It has no page, so it doesn't enter a link bundle, a ticket bundle, a draft or an impact answer, and doesn't count a section as linked. It isn't sent to the disprove step, because code already compared it. A judge's run doesn't touch it. Running `compare-tables` again replaces its own, and a decided one that went away is kept as `gone`.

## Requirements (2c, D99; contract `requirements` v1, being built)

The FSD stays the record. On top of it, one AI pass per section builds items, each quoting the FSD word for word. Status starts
`proposed`; only a person approves.

- `stangent req prepare|check <doc> <section>`, the usual loop. `spec-run.sh --req <doc> [--only <section>]` runs it in batches.
  `stangent req sections` lists sections with text; `stangent req show <id>` prints one item, never a whole file.
- **`stangent-requirement-writer`** returns requirements (kind, title, statement, quotes, acceptance criteria), definitions (glossary,
  data, roles, states, messages, outside systems, scope, success criteria, only when the FSD says something about them), journeys and
  scenarios made of requirement keys, questions for the BA, and background.
- **Code checks, one retry:** the schema; keys unique and pointing at something; no statement twice; every quote from the section word
  for word; every sentence cited or background. **Cited** means the quotes of requirements, criteria and definitions cover every word of it,
  whole words only (a piece under 4 words counts only as a whole sentence), and a table row must be quoted whole. **Background** is one sentence
  exactly as listed. A second failure fails the section; `--retry-failed` tries again.
- **`stangent-requirement-checker`** (fresh context, sees the section, the items, the background and the questions) says whether each item goes further than
  its quotes, naming the words (code checks they're in the item), whether each item cites a quote it has nothing to do with, and whether each background sentence holds
  a rule. Disputed ones go back to the writer once, then to the checker again; what's still disputed is recorded `disputed`. A dispute it couldn't back up and then dropped
  leaves the item `unchecked`.
- **Files,** committed, under `specs/requirements/`: `ids.json` (the permanent-id ledger: an id is given once), `history.jsonl` (every status move, `docs/foundation.md`), `runs.json` (cost, retries, counts), and per document
  `F-<id>.yaml` (one per section, following the FSD's section tree, parents listing children), `questions.yaml`, and two views written by code: `index.yaml` (one line per
  item, read first) and `glossary.yaml`. Working files are in `.stangent/req/`.
- **Ids** are plain numbers, assigned once: `F-`, `R-`, `D-` (definitions), `J-`, `S-`, `Q-`. On a re-run an item with the same quotes and words keeps its id, as does one reworded
  item alone on its quotes; ids whose quotes are gone are retired. A change to the title, statement, kind, quotes, criteria or the definitions it uses, or any answer from the checker but `ok`, drops an approved item to
  `proposed`. Reconcile (not built) replaces this with carrying items forward by code.
- **Links:** judged one requirement at a time when a section's requirements are built, unless `requirements-links` is off.
- **Not built yet:** approval, reconcile across documents and renumbering, a pass for clashes between sections, Jira and as-built sources, diagrams. Journeys are within one
  section, since extraction sees one section at a time.
